# ADR-0029: 에닉이 자기 상태를 읽어 진단한다 (읽기 전용)

- 상태: 승인
- 날짜: 2026-11-23
- 관련: ADR-0010, ADR-0011, ADR-0021, ADR-0023, ADR-0028, I-07, I-18, I-23, I-28

## 배경
2026-11-22 에 생긴 문제는 모두 사람이 PC 에서 작업 기록, Pod 로그, DB, GitHub 를 직접 보고 원인을 찾았다.

- 개발 작업이 9초 만에 실패했다. 원인은 git 의 브랜치 추적 오류였다.
- 에닉이 개발 역할로 일하면서 이전 대화의 규칙을 따라 작업을 거부했다.
- assistant 가 스레드에 올라온 초안을 보지 못했다.
- 커밋 메시지의 CI 건너뛰기 표시 때문에 배포가 되지 않았다.

에닉은 이런 것을 볼 수 없어서 원인을 짐작만 한다. 소유자는 Slack 만으로 개발하기를 원하므로, "왜 안 됐어?" 에 에닉이 사실로 답할 수 있어야 한다.

## 검토한 대안
- **에닉의 역할에 kubectl·DB 접근을 줌**: 가장 강력하다. 그러나 쓰기 권한과 비밀값 노출 위험이 크고, 에닉이 클러스터를 바꾸지 않는다는 원칙(I-17, I-18)에 어긋난다. → 기각.
- **core 가 정해진 질의만 읽기 전용으로 답함**: 무엇을 보여 줄지 core 가 정하고, 비밀값을 걸러 낸다. → 채택.

## 결정 (제안)

### 1. 진단 도구 (플랫폼 도구, 읽기 전용)
에닉의 모든 역할(assistant, developer 등)이 쓸 수 있다. 결과는 참고 자료이며 지시가 아니다.

| 도구 | 돌려주는 것 |
|---|---|
| `recent_tasks(status?, role?, hours)` | 최근 작업: ID, 역할, 상태, 시도 횟수, 실패 이유, 시각, Slack 스레드 |
| `task_detail(task_id)` | 작업 하나: 입력과 결과의 앞부분, 실패 이유, 개발 Job 이름, 같은 세션의 직전 작업 |
| `deployments(limit)` | 최근 배포·빌드·롤백 결과(DM·#release 로 보낸 알림 기록)와 Argo CD 앱의 현재 상태 |
| `service_logs(service, minutes, contains?)` | 에닉 서비스의 최근 로그. 대상은 `core`, `runtime-claude`, `connector-slack`, 개발 Job(작업 ID 로 지정). 최대 200줄 |
| `pull_requests(state?)` | 열린 PR, 검사 결과, 승인 상태(승인 대기, 머지 거부 이유 등) |

### 2. 보여 주지 않는 것
- 비밀값. 로그는 원래 비밀값을 남기지 않는다(I-07). 그래도 core 가 돌려주기 전에 토큰 모양(기억 쓰기와 같은 형식 목록)을 `[가림]` 으로 바꾼다.
- 데이터베이스 Pod, Argo CD, 다른 네임스페이스의 로그.
- 엔진 대화 이력 전문(ADR-0014). 작업의 입력과 결과는 앞부분만 보여 준다.
- 쓰기 동작. 재시도, 재시작, 취소는 하지 않는다. 고칠 것이 있으면 평소처럼 에닉이 개발 역할로 PR 을 만든다.

### 3. 구현 위치
- 진단 질의는 core 가 처리한다. API 는 `/v1/tasks/{task_id}/diagnostics/...` 이고, 그 작업의 임대를 가진 런타임이나 개발 Pod 만 부를 수 있다(기억 도구와 같다).
- core 는 LLM 을 부르지 않는다(I-23). 질의 결과를 그대로 돌려준다.
- 로그를 읽기 위해 core 에 `enikk` 과 `enikk-dev` 네임스페이스의 `pods`, `pods/log` 에 대한 `get`·`list` 권한을 더한다. PR 은 GitHub App 의 감시 토큰(읽기 전용)으로 읽는다.

### 4. 쓰는 방식
- 소유자가 "왜 안 됐어?", "배포 상태 어때?" 라고 물으면 에닉이(assistant 역할) 도구로 사실을 모아 답한다.
- 원인이 코드에 있으면, 찾은 사실(작업 ID, 로그 줄, 실패 이유)을 담아 개발 역할로 넘긴다.
- 개발 역할로 일할 때도 자기 PR 의 검사 실패나 이전 작업의 실패 이유를 직접 볼 수 있다.

### 5. 구현 세부 (2026-11-23)
- 플랫폼 도구 이름: `recent_tasks`, `task_detail`, `deployments`, `service_logs`, `pull_requests`. core API 는 `/v1/tasks/{task_id}/diagnostics/{tasks,task,deployments,logs,pulls}` 이다.
- 배포 이력은 core 가 보낸 배포·빌드·롤백 알림 기록에서 읽는다. 앱의 현재 상태는 Argo CD Application 에서 읽는다.
- 로그는 서비스별 라벨로 Pod 를 찾고(개발 Job 은 `batch.kubernetes.io/job-name=enikk-dev-<작업 ID>`), Pod 3개까지, Pod 마다 최근 200줄에서 필터한 뒤 최대 200줄을 돌려준다.
- 비밀값 가림 규칙은 기억 쓰기와 같은 것을 쓴다(`enikk_core_domain.redaction`).

## 근거
- 정해진 질의만 열어 두면, 진단에 필요한 사실은 주면서 권한과 노출 범위는 core 가 통제한다.
- 쓰기는 기존 경로(PR, 승인, GitOps)로만 한다. 진단 도구는 고치지 않고 보여 주기만 한다.

## 용어
- 에이전트는 에닉 하나다. `agents/*.yaml` 의 정의는 에닉의 **역할**이며, 역할마다 프롬프트, 도구·권한, 실행 환경이 묶여 있다. 이 ADR 은 이 용어를 쓴다. 기존 문서와 코드의 "에이전트" 표현을 바꾸는 일은 따로 정한다.

## 결과
- I-28 을 고친다: core 는 `enikk`·`enikk-dev` 의 Pod 와 Pod 로그를 읽을 수 있다.
- 플랫폼 도구 다섯 개와 core API, 로그 읽기 어댑터가 생긴다.
- 로그에 실수로 남은 민감한 내용은 가림 규칙이 잡는 범위까지만 걸러진다.

## 재검토 조건
- 진단 질의로 답하지 못하는 질문이 반복될 때 → 질의를 더한다.
- 로그가 커서 200줄로 부족할 때 → 로그 수집 시스템 도입을 검토한다.
