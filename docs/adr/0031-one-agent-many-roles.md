# ADR-0031: 에이전트는 에닉 하나이고, `agents/*.yaml` 은 에닉의 역할이다

- 상태: 승인
- 날짜: 2026-11-23
- 관련: ADR-0003, ADR-0005, ADR-0007, ADR-0021, ADR-0022, ADR-0027, ADR-0029, I-10, I-11, I-12, I-14, I-15, I-17, I-18, I-19, I-20, I-21, I-22, I-24, I-32

## 배경
지금까지 문서는 "에이전트"를 두 뜻으로 썼다.

- 소유자가 Slack 에서 대화하는 상대 전체(에닉). 예: "에이전트는 자기 변경을 승인할 수 없다"(I-19).
- `agents/*.yaml` 정의 하나. 예: "개발 에이전트", "메인 대화 에이전트", "엔진이 다른 에이전트 사이의 위임"(I-12).

그래서 "다른 에이전트"가 다른 시스템인지, 같은 에닉의 다른 정의인지 문장마다 읽는 사람이 판단해야 했다.
ADR-0029 '용어' 절은 "에이전트는 에닉 하나, 정의는 에닉의 역할"이라는 용어를 그 ADR 안에서만 쓰기로 하고, 기존 문서와 코드의 표현을 바꾸는 일은 따로 정한다고 남겼다. 이 ADR 이 그 결정이다.

## 검토한 대안
- **(가) 문서 용어만 "역할"로 바꾸고 코드 이름은 그대로 둔다**: 채택 (소유자 결정, 2026-11-23).
- **(나) 코드 이름까지 바꾼다** (`AgentDefinition` → `RoleDefinition`, `agents/` → `roles/` 등): 이름이 문서와 맞는다. 그러나 계약 모델, DB 열, API, 설정 키, 환경변수, Helm values, 이미지·앱 이름, Langfuse 프롬프트 참조, 브랜치 이름(`agent/<id>`)까지 함께 바뀌어 expand/contract(I-34)로 여러 번 나눠 배포해야 한다. 얻는 것은 이름의 일관성뿐이다. → 기각.
- **(다) 지금처럼 둔다**: 비용은 없지만 위의 모호함이 남는다. → 기각.

## 결정

### 1. 용어
- **에이전트는 에닉 하나뿐이다.** 소유자가 Slack 에서 대화하는 상대이며, 아래 모든 역할을 합친 것이다.
- **역할**: `agents/*.yaml` 하나하나. 프롬프트, 도구·권한, 실행 환경(엔진, `execution`)을 묶은 것이다. "assistant 역할", "developer 역할"처럼 정의 파일의 이름으로 부른다.
- **역할 정의**: 역할을 적은 파일(`agents/*.yaml`). 형식은 ADR-0005 를 따른다.

### 2. 코드 이름은 바꾸지 않는다
다음은 그대로 둔다. 문서에서 인용할 때도 원래 이름을 쓴다.

- 클래스·타입·함수 이름(`AgentDefinition` 등), 폴더 이름(`agents/`), 설정 키, 환경변수 이름, 로그 문구.
- 앱·이미지·ServiceAccount 이름(`enikk-dev-agent` 등), 브랜치 이름(`agent/<id>`), 파일 이름 `AGENTS.md`.
- Langfuse 프롬프트 이름(`assistant`, `developer`).

코드 이름은 구현 개념("정의 파일을 읽어 실행하는 단위")을 가리키고, 문서 용어는 소유자가 보는 개념("에닉이 맡는 일")을 가리킨다. 둘이 다른 것은 의도한 것이다. 바꾸는 비용(대안 (나))이 크고 동작에는 차이가 없다.

### 3. 기존 표현의 대응
문서를 고치거나 새로 쓸 때 다음처럼 쓴다.

| 기존 표현 | 새 표현 |
|---|---|
| 에이전트 (에닉 전체를 가리킬 때) | 에닉 |
| 에이전트 (정의 하나를 가리킬 때) | 역할 |
| 에이전트 정의 | 역할 정의 (`agents/*.yaml`) |
| 개발 에이전트, 격리 개발 에이전트 | 에닉의 개발 역할(developer 역할) |
| 메인 대화 에이전트 | 에닉의 대화 역할(assistant 역할) |
| 실행용 에이전트 | 실행용 역할 |
| 다른 에이전트, 엔진이 다른 에이전트 | 다른 역할, 엔진이 다른 역할 |
| 스레드의 에이전트, 그 스레드 에이전트 | 스레드의 역할 |
| Slack 과 에이전트의 연결 규칙, 에이전트 매핑 | Slack 과 역할의 연결 규칙, 역할 매핑 |
| Claude 에이전트, Gemini 에이전트 | Claude 엔진 역할, Gemini 엔진 역할 |
| 에이전트 런타임 | 런타임 |
| 에이전트 자기 개선 | 에닉의 자기 개선 |
| 개인용 AI 에이전트 플랫폼 | 개인용 AI 에이전트 에닉(과 그 플랫폼) |

- **예외**: 에닉 바깥의 일반 용어인 "코딩 에이전트"(`AGENTS.md` 를 읽는 Claude Code 같은 도구)는 그대로 쓴다. 에닉의 developer 역할도 그중 하나다.

### 4. 적용 범위
- 이 ADR 과 함께 불변식, `AGENTS.md`, ADR 목록의 제목 문구, `docs/architecture/`, `docs/plan/`, `docs/development/`, 루트 `README.md`, `deploy/github/README.md` 의 표현을 고친다.
- **기존 ADR 본문(ADR-0001 ~ ADR-0030)은 고치지 않는다.** 결정 당시의 기록이기 때문이다. 그 본문의 "에이전트"는 위 대응표로 읽는다. 용어만 바뀌었고 결정은 바뀌지 않았으므로 상태에 대체 표시를 달지 않는다. ADR 목록에만 이 사실을 적는다.
- 코드 안의 사람이 읽는 문구(Slack 메시지 등)와 Langfuse 프롬프트 본문은 이 ADR 로 바꾸지 않는다. 필요하면 따로 바꾼다.

## 근거
- 하나의 말이 하나의 뜻을 가지면, 불변식처럼 정확해야 하는 문장을 읽을 때 해석이 갈리지 않는다.
- 소유자에게 에닉은 하나의 상대이고, 역할은 에닉이 맡는 일의 구분이다. 문서가 이 모습을 그대로 따른다.
- 코드 이름 변경은 동작 차이 없이 배포 위험만 늘린다.

## 결과
- 문서와 코드 이름이 다르다(역할 ↔ `Agent*`). 문서에서 코드를 인용할 때 원래 이름을 쓰고, 처음 나올 때 "역할 정의(`AgentDefinition`)"처럼 함께 적는다.
- 기존 ADR 본문은 옛 표현을 쓴다. 읽을 때 대응표를 참고해야 한다.
- 불변식 문장 몇 개가 "에이전트" 대신 "에닉"이나 "역할"을 쓴다. 지키는 조건은 그대로다.

## 재검토 조건
- 에닉 말고 다른 에이전트(다른 사용자의 봇, 외부 에이전트와의 협업 등)를 들이게 될 때.
- 코드 이름을 바꿀 다른 큰 변경(계약 버전 변경 등)이 생겨 함께 바꾸는 비용이 작아질 때.
