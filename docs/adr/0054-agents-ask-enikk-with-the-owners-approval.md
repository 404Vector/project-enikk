# ADR-0054: 에이전트가 에닉에게 일을 요청하고, 소유자가 그 스레드에서 허가한다

- 상태: 승인
- 날짜: 2026-11-28
- 관련: ADR-0041, ADR-0045, ADR-0047, ADR-0051, I-01, I-11, I-12, I-29

> 결정은 2026-11-28 소유자가 Slack 스레드에서 확정했다: 리타·아르카나가 에닉에게 일을 요청할 수 있게 하되, 소유자의 허가를 거쳐 진행한다. 허가는 승인 채널이 아니라 요청한 스레드에서 바로 한다. 결과는 요청한 에이전트에게 돌아가고, 결정되지 않은 요청은 24시간 뒤 거절되며, 대화 스레드에서만 쓴다.

## 배경

- 위임(ADR-0047)은 에닉에서 다른 에이전트로 가는 한 방향이다. 리타·아르카나는 자기 정의의 도구만 가지므로(ADR-0045 §7, ADR-0051), 도구 추가나 플랫폼 변경처럼 에닉만 할 수 있는 일이 생기면 소유자가 에닉의 스레드로 옮겨 다시 설명해야 했다.
- 에닉은 모든 권한을 갖는다(ADR-0041 §1). 다른 에이전트가 에닉에게 일을 맡길 수 있으면 그 에이전트가 에닉의 권한을 빌려 쓰는 셈이다. 다른 에이전트가 읽은 웹 문서나 파일의 지시가 요청문에 섞일 수 있다.
- 비슷한 흐름으로 아르카나의 노트 변경 요청(ADR-0051 §4)이 있다. 그 카드는 승인 채널에 간다.

## 검토한 대안

- **위임을 양방향으로 연다(`delegates` 에 에닉)**: 코드가 가장 적다 / 소유자의 확인 없이 에닉의 권한이 다른 에이전트에게 열린다. → 기각.
- **승인 채널의 카드**: 기존 승인 흐름과 같다 / 소유자는 대화하던 스레드에서 바로 결정하기를 원했다. 승인 채널은 `main` 머지와 프롬프트 승격처럼 되돌리기 어려운 결정에 남긴다. → 기각.
- **요청한 스레드의 카드 + 허가하면 위임과 같은 하위 세션에서 실행** (선택).

## 결정

### 1. 정의
- 정의의 `asks` 가 일을 요청할 수 있는 에이전트를 나열한다(git 에서만 바뀜, I-16). `agents/rita.yaml`·`agents/arcana.yaml` 은 `asks: [enikk]`.
- 자기 자신은 대상이 될 수 없고, 같은 에이전트를 `delegates` 와 `asks` 에 함께 둘 수 없다. 대상은 공용 runtime 에서 도는 정의여야 한다(catalog 검사).

### 2. 요청
- `asks` 가 있는 정의의 스레드 세션은 플랫폼 도구 `ask_agent(agent, request, reason)`(Claude 에게는 `mcp__enikk__ask_agent`)를 받는다. 요청문은 20000자, 이유는 500자 이하다. 비밀값으로 보이는 글은 거부한다.
- core 는 `POST /v1/tasks/{id}/ask` 로 받는다. 호출 작업의 임대가 살아 있고, 그 세션이 Slack 스레드 자신의 세션이며(`reply_to` 없음, 위임·요청으로 생긴 하위 세션은 요청하지 못함), 대상이 그 정의의 `asks` 에 있을 때만 받는다.
- 요청은 `asks` 표에 남고(`requested`), 아무것도 실행하지 않는다. 도구는 곧바로 돌아온다.

### 3. 카드
- core 는 알림(`AskCard`)을 넣고, connector 가 그것을 요청한 스레드 안에 그 채널의 표시 이름·아이콘(ADR-0045 §3)으로 올린다. 승인 채널에는 아무것도 가지 않는다. 스레드에 올릴 수 없으면 소유자 DM 으로 보낸다.
- 카드에는 요청한 에이전트와 대상, 이유, 요청문 전체(20000자 이하라 섹션 10개 안에 모두 들어감), 만료 시각, [허가]·[거절] 버튼이 있다. [허가]는 확인 창을 거친다.
- 버튼은 소유자만 누를 수 있다(I-01). connector 가 누른 사람을 확인하고, core 도 결정한 사람이 소유자인지 다시 확인한다. 누르면 버튼이 결과 줄로 바뀐다.

### 4. 결정
- **허가**: core 가 위임과 같은 하위 세션(ADR-0047 §2, `uuid5(부모 세션, 대상)`, `reply_to` 는 요청한 스레드)에 대상의 작업을 넣는다. 원본 이벤트 ID 는 `ask:<요청>` 이고, 입력은 `[요청]` 머리말(요청한 에이전트가 쓴 글이며 소유자의 말이 아님, 이유)과 요청문이다. 하위 작업은 대상 정의의 도구로 돈다.
- **결과**: 하위 작업이 끝나면 위임과 같은 길(ADR-0047 §3)로 요청한 스레드를 깨운다. 이벤트 머리말은 `[이벤트] <대상> 의 요청 작업 완료|실패` 다. 결과는 요청한 에이전트가 이어서 소유자에게 전한다.
- **거절**: 요청한 스레드를 `[이벤트] <대상> 에게 보낸 요청 소유자가 거절함` 으로 깨운다.
- **만료**: 24시간(core 설정 `asks.expires_hours`, 환경변수 `ENIKK_CORE_ASKS__EXPIRES_HOURS`) 안에 결정되지 않으면 core 의 주기 작업(작업 임대 회수와 같은 루프)이 거절로 닫고, 스레드에 그 사실을 올리고, 요청한 스레드를 깨운다. 만료 뒤에 누른 버튼은 아무것도 실행하지 않는다.
- 한 번 결정된 요청은 다시 결정되지 않는다.

### 5. 취소와 파일
- 스레드의 [취소] 는 그 스레드가 요청해 허가된 하위 작업도 취소한다(ADR-0047 §4 와 같음).
- runtime 은 요청한 세션의 작업 공간에 대상 하위 세션의 tmp 를 더한다(ADR-0047 §5 와 같음).

## 근거
- 에닉의 권한을 빌리는 길은 소유자의 [허가] 하나로만 열린다. 카드에 요청문 전체를 보이므로 소유자는 요약이 아니라 실제로 실행될 글을 보고 결정한다.
- `main` 머지와 프롬프트 승격은 이 흐름과 상관없이 승인 채널을 거친다(I-19). 허가된 에닉의 작업이 PR 을 열어도 머지는 그대로 소유자의 승인이 필요하다.
- 하위 세션, 깨우기, 취소 전파, 작업 공간은 위임의 것을 그대로 쓴다. 새로 생기는 것은 요청 표와 카드뿐이다.

## 결과
- 하위 세션은 요청하지도 위임하지도 못하므로 리타 → 에닉 → 리타 같은 고리는 생기지 않는다.
- 허가된 에닉의 작업은 요청한 채널의 스레드에 처리 중 [취소] 버튼을 붙이고, 표시는 그 채널의 것이다(ADR-0047 결과와 같음).
- 위임이 끝났다는 스레드 안내는 "결과는 이 스레드에서 이어서 전합니다"로 바꿨다. 요청에서는 이어 전하는 쪽이 에닉이 아니기 때문이다.
- 마이그레이션 0017 이 `asks` 표를 만든다.
- 프롬프트(rita, arcana)에 도구를 언제 쓸지 적는 것은 이 변경과 별도로 후보를 만들어 소유자가 승격한다.

### 바뀌는 불변식
- I-11: 스레드 세션은 `asks` 의 에이전트에 일을 요청할 수 있고, 소유자가 그 스레드에서 허가한 요청만 하위 세션에서 돈다.
- I-12: 요청에서도 하위 세션에 넘기는 것은 요청문(과 이유)뿐, 돌아오는 것은 결과 본문뿐이다.
- I-29: 스레드의 [취소] 는 그 스레드의 요청으로 생긴 하위 작업도 취소한다.

## 재검토 조건
- 요청이 잦아 소유자의 허가가 부담이 될 때(종류별 자동 허가를 검토).
- 리타·아르카나 말고 다른 에이전트에도 요청을 열 때, 또는 에닉 외의 대상이 생길 때.
- 예약 세션에서도 요청해야 할 일이 생길 때.
