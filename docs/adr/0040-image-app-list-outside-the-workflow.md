# ADR-0040: 이미지를 만들 앱 목록을 워크플로 밖에 둔다

- 상태: 승인
- 날짜: 2026-11-24
- 관련: ADR-0008, ADR-0024, ADR-0037, ADR-0038, ADR-0039, I-20

## 배경
- `images` 워크플로는 `verify`·`build`·`publish` 세 잡의 matrix 에 앱 이름을 직접 적었다.
- 스레드 세션은 `.github/workflows/` 를 바꿀 수 없다(ADR-0037 §2b). 그래서 앱을 하나 더할 때마다 소유자가 워크플로를 직접 고쳐야 했다(ADR-0039 S2 의 `scheduler`).

## 검토한 대안
- **그대로 둔다**: 바꿀 것이 없다 / 앱이 늘 때마다 소유자 손이 필요하다. → 기각(소유자).
- **`deploy/helm/` 의 디렉토리 목록에서 만든다**: 새 파일이 없다 / 차트 없는 앱(예: 이미지만 필요한 작업)을 표현할 수 없고, 빌드 대상이 암묵적이 된다. → 기각.
- **목록 파일 `deploy/images.yaml`**: 빌드 대상이 한 파일에 보인다. 민감 경로로 두면 바뀔 때 승인 화면에 경고가 뜬다. → 채택.

## 결정
- 빌드할 앱 목록의 원본은 `deploy/images.yaml` 의 `apps` 다. 워크플로의 첫 잡(`apps`)이 이것을 읽어 JSON 배열로 넘기고, 세 잡의 matrix 가 이를 쓴다.
- 이름은 `^[a-z][a-z0-9-]{0,40}$` 만 허용한다. 워크플로는 맞지 않으면 실패한다. 테스트(`ops-cli` 의 `test_images.py`)는 이름 규칙, 앱 패키지 이름(`enikk-<앱>`), `deploy/helm/` 의 모든 차트가 목록에 있는지를 확인한다.
- `deploy/images.yaml` 은 민감 경로다(I-20).
- 워크플로의 빌드 방식, 권한, 비밀값, 게시 단계는 그대로 워크플로에 있고 소유자만 바꾼다.

## 근거
- 목록이 바꾸는 것은 "어느 앱을 빌드하나" 뿐이다. 빌드에 쓰는 Dockerfile 과 권한은 같으므로, 스레드 세션이 목록을 바꿔도 새로 얻는 권한이 없다.
- 이름을 정규식으로 제한하므로 목록 값이 셸이나 이미지 이름에 다른 내용을 넣을 수 없다.

## 결과
- 소유자는 워크플로를 한 번 고친다. 그 뒤로 앱 추가는 PR 하나로 끝난다.
- 목록에서 앱을 빼면 그 앱의 새 이미지가 더는 게시되지 않는다. 운영 중인 Deployment 는 마지막 태그로 계속 돈다.
- `deploy/images.yaml` 만 바꾼 커밋도 이미지를 빌드하도록 워크플로의 `paths` 에 이 파일을 더한다.

## 재검토 조건
- 앱마다 Dockerfile 이나 빌드 인자가 달라질 때.
