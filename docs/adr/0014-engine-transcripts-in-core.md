# ADR-0014: 엔진 대화 이력(트랜스크립트)은 core 가 저장한다

- 상태: 승인
- 날짜: 2026-11-22
- 관련: ADR-0010, ADR-0011, ADR-0012, I-11, I-25, I-26, I-27, I-29, I-31, P-13

## 배경
Claude Agent SDK 는 대화 이력(트랜스크립트)을 실행 중인 머신의 로컬 파일에 쓴다(`~/.claude/projects/<cwd 에서 만든 키>/<세션 ID>.jsonl`).
이전 대화를 이어 가려면(resume) 같은 파일이 있어야 한다.

이 동작은 런타임이 상태를 갖지 않는다는 원칙(I-25)과 충돌한다. Pod 가 재시작되거나 다른 Pod 가 작업을 받으면 이력이 사라져 대화가 끊긴다.

SDK 에는 이 문제를 위한 확장 지점이 있다. `SessionStore` 어댑터를 주면 SDK 가 이력 항목을 외부 저장소에도 기록하고(`append`), 이어 갈 때 외부 저장소에서 읽는다(`load`).
- 이력 항목은 SDK 가 정한 JSON 객체다. 형식은 SDK 버전에 따라 바뀔 수 있다.
- 같은 항목이 다시 오면 `uuid` 필드로 중복을 거른다.
- 서브에이전트 이력은 같은 세션 아래 `subpath` 로 구분된다.
- 출처: Claude Agent SDK 문서 "Session storage" (M3 계획 때 확인, 2026-11).

## 검토한 대안
- **런타임에 영구 볼륨(PVC) 연결**: SDK 를 그대로 쓸 수 있다. 그러나 런타임이 상태를 갖게 되고(I-25 위반), 런타임을 여러 개로 늘리면 볼륨 공유 문제가 생긴다. → 기각.
- **이어 가기 없이 매번 새 세션**: core 의 작업 기록으로 맥락을 다시 만들어 넣는다. 도구 사용 내역 같은 엔진 내부 맥락이 사라지고, 프롬프트 캐시도 활용하지 못한다. → 기각.
- **런타임이 DB 에 직접 접속**: DB 에는 core 만 접근한다는 원칙(I-26)에 어긋난다. → 기각.

## 결정

### 1. 저장 위치와 경로
- 런타임의 `SessionStore` 어댑터가 core API 를 거쳐 core 의 Postgres(`transcript_entries` 테이블)에 이력을 저장한다.
- core API 는 세 개다.
  - `POST /v1/tasks/{task_id}/transcript/append`
  - `POST /v1/tasks/{task_id}/transcript/load`
  - `POST /v1/tasks/{task_id}/transcript/subpaths`

### 2. 접근 범위: 활성 임대
- 모든 요청에는 그 작업의 **활성 임대 ID** 가 있어야 한다.
- core 는 임대가 유효한지 확인한 뒤, 그 작업이 속한 **core 세션** 의 이력에만 접근을 허용한다.
- 처리 규칙은 다음과 같다.
  - 다른 엔진의 작업이면 404 이다.
  - 임대가 끝났거나 만료됐거나 맞지 않으면 409 이다.
  - 커넥터나 개발 에이전트가 호출하면 403 이다.
- 따라서 런타임은 지금 맡은 작업의 대화 이력만 읽고 쓸 수 있다.
- 한 세션에서 동시에 실행되는 작업은 하나뿐이므로(I-29), 한 세션의 이력에 동시에 쓰는 일은 없다.

### 3. 저장 키와 순서
- 저장 키는 `(core 세션, project_key, engine_session_id, subpath)` 이다.
  - `project_key` 와 `engine_session_id` 는 SDK 가 정한 값을 그대로 쓴다.
  - 주 이력의 `subpath` 는 빈 문자열로 저장한다.
- 항목은 추가된 순서대로 돌려준다.
- 같은 키에서 이미 저장된 `uuid` 를 가진 항목, 그리고 한 요청 안에서 반복된 `uuid` 는 건너뛴다. `uuid` 가 없는 항목은 매번 저장한다.
- 한 번에 추가할 수 있는 항목은 최대 1,000개다.

### 4. 원칙 예외: 해석하지 않는 JSON
- 이력 항목은 경계를 넘을 때 `dict[str, JsonValue]` 로만 검증한다. 즉 JSON 값인지만 확인한다.
- core 는 `uuid` 필드 말고는 내용을 해석하지 않고 JSONB 로 보관한다.
- 이것은 "경계를 넘는 데이터는 pydantic 모델로만"(P-13, I-27)의 **유일한 예외** 다. 형식의 주인이 우리가 아니라 SDK 이고, 우리가 해석할 필요가 없기 때문이다.
- 예외는 이 계약(`enikk_contracts.transcripts`)과 `transcript_entries` 테이블로 한정한다.

### 5. 보존
- 이력은 core 세션과 함께 보존한다. 삭제·정리 정책은 아직 두지 않는다.

## 근거
- 상태가 core 한 곳에 모이므로 런타임 Pod 가 바뀌어도 대화가 이어진다(I-25).
- SDK 가 공식으로 제공하는 확장 지점을 쓰므로 SDK 내부 파일 형식을 직접 다루지 않는다.
- 임대를 기준으로 권한을 주면 "지금 이 작업을 맡은 런타임" 만 이력에 접근할 수 있다. 커넥터나 다른 엔진은 접근할 수 없다.

## 결과
- 대화 내용 전체(도구 호출과 결과 포함)가 core DB 에 쌓인다. DB 백업이 곧 대화 이력 백업이다.
- 런타임이 이력을 쓰는 동안 core 가 응답하지 않으면 SDK 의 기록이 실패한다. 이때는 런타임이 작업을 재시도 가능한 실패로 보고한다(PR-4 에서 구현).
- `project_key` 는 SDK 가 작업 디렉터리(cwd)에서 만든다. 런타임은 모든 Pod 에서 같은 작업 디렉터리를 써야 한다.
- 이력이 커지면 매번 모두 읽는 `load` 가 느려질 수 있다.
- I-31 을 추가한다. I-27 에는 예외를 명시한다.

## 재검토 조건
- SDK 의 `SessionStore` 인터페이스가 바뀌거나 없어질 때.
- 이력 크기 때문에 `load` 나 DB 용량이 문제가 될 때. 이때는 압축, 보존 기간, 잘라 내기를 검토한다.
- 두 번째 엔진(Gemini)도 같은 방식이 필요해질 때. 계약은 엔진 중립적으로 만들었으므로 재사용할 수 있는지 확인한다.
