# ADR-0012: enikk-core 골격 구현 세부 결정

- 상태: 승인
- 날짜: 2026-11-21
- 관련: ADR-0005, ADR-0010, ADR-0011, I-11, I-18, I-24, I-26, I-28, I-29

## 배경
ADR-0011 은 저장소·큐·API·인증의 방향을 정했다. M2 구현에 앞서 그 방향을 코드로 옮길 때 필요한 세부 선택을 정한다.

## 결정

### 1. 영속성 통합 테스트: testcontainers
- 영속성 어댑터의 통합 테스트는 **testcontainers** 로 실제 Postgres 컨테이너를 띄워 실행한다.
- 컨테이너 이미지는 클러스터(CloudNativePG)와 **같은 메이저 버전**을 쓴다.
- 검토한 대안: CI 서비스 컨테이너. CI 에서만 동작하고 로컬에는 별도 Postgres 와 접속 설정이 필요해 실행 경로가 둘로 갈린다. → 기각.
- Docker 를 쓸 수 없는 환경에서는 통합 테스트를 건너뛰지 않고 **실패**시킨다. 검사를 조용히 통과시키지 않기 위해서다.

### 2. DB 접근: 비동기 SQLAlchemy + psycopg 3
- core 는 FastAPI 비동기 핸들러에서 롱 폴링을 처리하므로 DB 접근도 비동기(`AsyncSession`, 드라이버 psycopg 3)로 한다.
- 도메인 포트(레포지토리, UoW, 큐)는 `async` 메서드로 정의한다.

### 3. 작업 큐: 작업 테이블 자체가 큐
- 별도 큐 테이블을 두지 않는다. `QUEUED` 상태의 작업 행이 곧 큐 항목이며, 작업 저장과 큐 등록이 같은 행 쓰기이므로 원자적이다.
- `JobQueue` 포트는 "다음 작업 확보(`claim_next`)"와 "임대 만료 작업 확보(`claim_expired`)"만 정의한다.
  Postgres 구현은 `SELECT ... FOR UPDATE SKIP LOCKED` 를 쓴다.
- **세션당 실행 중 작업은 최대 1개**다 (I-29). 같은 스레드의 다음 메시지는 앞 작업이 끝난 뒤 배정된다.
  엔진 세션 하나에 두 작업이 동시에 쓰면 대화 이력이 섞이기 때문이다.
  Postgres 구현은 작업 행과 세션 행을 함께 잠가(`FOR UPDATE OF tasks, sessions SKIP LOCKED`) 두 런타임이 같은 세션의 작업을 동시에 가져가지 못하게 한다.
- 큐를 다른 저장소로 바꾸면 ADR-0011 의 결과에 적힌 대로 아웃박스 패턴을 함께 도입한다.

### 4. 롱 폴링: 요청 안에서 주기적 재조회
- 작업 임대·outbox 조회 요청은 최대 대기 시간(기본 20초, 상한 25초) 동안 1초 간격으로 다시 조회한다.
- 지연이 문제가 되면 Postgres `LISTEN/NOTIFY` 로 바꾼다. 바뀌는 곳은 core 유스케이스의 대기 부분뿐이다.

### 5. 마이그레이션: Argo CD PreSync Job
- core 이미지에 `enikk-core migrate` 명령을 두고, core Helm 차트의 **PreSync 훅 Job** 으로 실행한다.
- 마이그레이션이 실패하면 동기화가 멈추고 새 버전의 core 는 뜨지 않는다.
- 검토한 대안: core 시작 시 실행. 복제본끼리 경쟁하고, 실패해도 이전 스키마로 새 코드가 뜰 수 있다. → 기각.

### 6. 에이전트 정의 전달: core 이미지에 포함
- `agents/` 디렉토리를 core 이미지에 복사하고, core 는 시작할 때 모든 정의를 읽어 검증한다. 하나라도 잘못되면 시작하지 않는다.
- 정의를 바꾸면 이미지가 다시 빌드되어 GitOps 로 배포된다. git 이 원본이라는 I-24 가 그대로 유지된다.
- 저장소의 모든 정의가 유효한지는 core 테스트에서도 검사한다.

### 7. 클러스터 검증: ops-cli smoke
- `enikk-ops smoke core` 는 검증용 Pod 를 띄우지 않는다. 대상 ServiceAccount 의 audience=`enikk-core` 토큰을 TokenRequest 로 발급받고, port-forward 로 core 를 호출한다.
- 운영 리소스를 바꾸지 않으므로 I-18 에 해당하지 않으며, core 는 실제 TokenReview 경로로 검증한다.
- 커넥터·런타임 ServiceAccount 는 해당 앱이 생기기 전에 `deploy/k8s/identities/` 에 먼저 둔다.

### 8. API 형식
- 모든 API 는 `/v1` 아래에 있고, 상태를 바꾸거나 대기하는 요청은 `POST` + 계약 모델 본문을 쓴다.
- 오류 응답은 계약 `ErrorResponse`(코드 + 메시지) 하나로 통일한다. 클라이언트는 코드별 예외로 바꾼다.
- 엔드포인트마다 허용 역할을 선언하며, 선언이 없는 엔드포인트가 있으면 앱 생성이 실패한다 (I-28).
- 런타임의 엔진과 커넥터의 종류는 요청 본문이 아니라 **인증된 ServiceAccount 의 역할**에서 정해진다.
  런타임은 자기 엔진의 작업만 받을 수 있다.

### 9. 에이전트 정의 스키마 v0
- ADR-0005 초안 대비 변경:
  - 실행 한도의 시간은 `timeout_seconds`(정수)로 쓴다. 단위 문자열(`10m`) 해석을 두지 않기 위해서다.
  - `engine_options` 는 v0 에 두지 않는다. 필요한 첫 사례가 생기면 엔진별 모델로 추가한다(임의 키-값 금지, P-13).
- 프롬프트 참조는 `label` 과 `version` 중 정확히 하나를 가진다.

## 결과
- 같은 스레드의 메시지는 순서대로 처리된다. 대신 앞 작업이 오래 걸리면 다음 메시지도 기다린다.
- 통합 테스트를 돌리려면 Docker 가 필요하다 (로컬 WSL, GitHub 호스팅 runner 모두 제공).
- 정의 파일 변경도 core 재배포를 거친다. 정의 변경 빈도가 높아 재배포가 부담이 되면 재검토한다.

## 재검토 조건
- 롱 폴링 지연이나 DB 부하가 체감될 때 (4번).
- 에이전트 정의를 배포 없이 바꿔야 할 필요가 생길 때 (6번).
