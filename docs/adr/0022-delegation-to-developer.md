# ADR-0022: assistant 가 개발 에이전트에 작업을 위임한다

- 상태: 승인
- 날짜: 2026-11-22
- 관련: ADR-0003, ADR-0004, ADR-0005, ADR-0007, ADR-0017, ADR-0020, ADR-0021, I-05, I-11, I-12, I-14, I-17

## 배경
ADR-0007 은 Slack 에 응답하는 실행용 에이전트가 변경 요청을 받으면 개발 에이전트에 위임만 하도록 정했다.
소유자는 별도 채널이나 명령 대신, assistant 가 대화에서 변경 요청인지 판단해 넘기는 방식을 골랐다.
에이전트 정의에는 `delegates` 항목이 있지만(ADR-0005) 아직 동작하지 않는다.

## 검토한 대안
- **개발 전용 Slack 채널을 `developer` 에이전트에 연결**: 구현이 가장 단순하다. 그러나 소유자가 대화를 나눠야 한다. → 소유자 결정으로 기각.
- **assistant 가 위임 도구를 호출하고, core 가 하위 작업을 만든다**: 채택.

## 결정

### 1. 위임 도구
- 런타임은 정의의 `delegates` 에 대상이 있는 에이전트에게만 `delegate` 도구를 준다. 도구 입력은 대상 에이전트 이름과 요청 본문(자연어)이다.
- 이 도구는 런타임 안에서 동작하는 플랫폼 도구이며, core API 만 호출한다. 외부 MCP 서버가 아니므로 agentgateway 를 거치지 않는다. I-05 는 외부 MCP 도구에 대한 규칙으로 명확히 한다.
- `agents/assistant.yaml` 은 `delegates: [developer]` 를 갖는다. assistant 자체의 도구 권한은 늘지 않는다(I-17).

### 2. 하위 작업
- core 는 위임을 받으면 부모 작업과 연결된 하위 작업을 만든다. 하위 작업은 **별도 세션**에서 실행되며, 부모 세션의 대화 이력을 넘기지 않는다. 넘기는 것은 요청 본문뿐이다(I-12).
- 하위 작업의 진행과 결과(PR 링크, 실패 이유)는 부모의 Slack 스레드에 게시한다. 승인 요청은 ADR-0020 에 따라 소유자 DM 으로 간다.
- 위임은 비동기다. assistant 는 하위 작업 접수만 확인하고 답을 마친다.
- 같은 스레드에서 수정을 요청하면 assistant 가 다시 위임한다. 이때 core 는 그 스레드의 기존 개발 세션을 이어서 쓴다. 개발 세션의 대화 이력은 그 세션 안에서만 이어진다.
- 실행 제한(ADR-0021)을 넘으면 위임을 거부하고, assistant 는 그 사실을 답한다.

### 3. 스레드와 세션
- Slack 스레드의 사용자 메시지는 계속 assistant 세션이 받는다(I-11).
- 하위 세션은 스레드에 출력만 하고, 스레드 메시지를 직접 받지 않는다.

## 근거
- 소유자는 하나의 대화에서 질문과 변경 요청을 섞어 쓸 수 있다.
- 위임 입력을 요청 본문으로 한정하면, 개발 에이전트가 받는 정보가 명시적이고 엔진 간 대화 이력 이동이 없다.
- 하위 작업을 core 가 만들므로 실행 제한, 상태, 이력이 core 한 곳에 모인다.

## 결과
- I-05 와 I-11 을 명확히 한다.
- assistant 가 변경 요청을 잘못 판단하면 불필요한 위임이 생긴다. 실행 제한과 소유자 승인이 그 비용을 제한한다.
- 위임 대상은 정의 파일(git)에서만 바뀐다(I-16).

## 재검토 조건
- 개발 에이전트 외의 위임 대상이 생길 때 → 동기 위임(결과를 기다려 답하는 방식) 필요 여부.
