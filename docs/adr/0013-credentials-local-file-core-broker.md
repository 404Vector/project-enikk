# ADR-0013: 비밀값은 소유자 PC 의 파일이 원본이고, core 가 서비스에 나눠 준다

- 상태: 승인
- 날짜: 2026-11-22
- 관련: ADR-0002, ADR-0007, ADR-0008, ADR-0011, I-02, I-07, I-18, I-21, I-28, I-30

## 배경
M3 부터 Slack 토큰, Claude 구독 토큰, Langfuse 키 같은 비밀값이 필요하다.
지금까지는 "소유자가 k8s Secret 을 직접 만든다"(I-07, I-21)는 원칙만 있었고, 다음이 정해지지 않았다.

- 비밀값의 원본을 어디에 둘 것인가. 클러스터(Docker Desktop k8s)는 쉽게 초기화되므로, 클러스터 안에만 두면 초기화할 때 모두 사라진다.
- 비밀값을 어떻게 관리할 것인가. 값을 넣고 빼는 일을 명령 하나로 할 수 있어야 한다.
- 어떤 서비스가 어떤 값을 받는가. 서비스마다 Secret 을 마운트하면 접근 경로가 서비스 수만큼 늘어난다.

소유자의 요구는 다음과 같다.

- 외부 클라우드 서비스에 비밀값을 맡기지 않는다.
- 원본은 이 PC 에 두되, Helm 차트·클러스터와 독립적이어야 한다.
- 원본 파일은 암호화하지 않는다. 문제가 생겼을 때 복구하기 쉬워야 한다.
- TLS 같은 무거운 장치는 지금 도입하지 않는다.

## 검토한 대안
- **GitHub 저장소 시크릿**: GitHub API 로는 값을 다시 읽을 수 없고, Actions 워크플로 안에서만 읽힌다. 클러스터로 옮기려면 PC 를 외부에 노출하거나 클러스터에 셀프호스티드 러너를 두고 쓰기 권한을 줘야 한다(I-18 위반). 또 같은 저장소의 브랜치 워크플로가 시크릿을 읽을 수 있어서, 자기 개선 에이전트가 만든 브랜치(ADR-0007)를 통한 유출 경로가 생긴다. → 기각.
- **외부 비밀 저장소 + External Secrets Operator**(1Password, Google Secret Manager 등): 클러스터를 초기화해도 자동으로 복구된다. 그러나 비밀값을 외부 서비스에 맡겨야 한다. → 소유자 요구로 기각.
- **PC 에서 OpenBao/Vault 를 직접 운영**: PC 를 재부팅할 때마다 잠금을 풀어야 하고, 서버를 운영·백업해야 한다. 1인 운영에는 과하다. → 기각.
- **SOPS/age 로 암호화한 파일**: 키를 잃으면 복구할 수 없다. → 소유자 요구(암호화하지 않음)로 기각.
- **서비스마다 k8s Secret 을 마운트**: 단순하다. 그러나 비밀값에 접근하는 경로가 서비스 수만큼 생기고, 누가 무엇을 받는지가 여러 차트에 흩어진다. → 기각.

## 결정

### 1. 원본: 소유자 PC 의 평문 파일
- 비밀값의 원본은 소유자 PC(WSL)의 `~/.config/enikk/secrets.yaml` 이다. 평문 YAML 이다.
- 파일 권한은 0600, 디렉터리 권한은 0700 이다. 다른 사용자가 읽을 수 있는 권한이면 CLI 가 읽기를 거부한다.
- 이 파일은 git 저장소 밖에 있으며 저장소에 넣지 않는다.
- 백업은 소유자가 직접 한다. 평문이므로 백업 매체도 비밀값과 같은 수준으로 보관한다.

### 2. 관리: `enikk-ops secret`
| 명령 | 동작 |
|---|---|
| `secret set <이름>` | 숨김 입력으로 값을 받아 파일에 저장한다. 값은 명령 인자로 받지 않는다. |
| `secret unset <이름>` | 파일에서 지운다. |
| `secret list` | 이름과 수정 시각만 보여 준다. 값은 출력하지 않는다. |
| `secret sync` | 파일의 모든 값을 클러스터의 Secret `enikk-core-credentials` 에 반영한다. 파일에 없는 키는 Secret 에서도 지워진다. |

- 쓸 수 있는 비밀값 이름은 계약 패키지의 `CredentialName` 에 정의된 것뿐이다. 이름은 git 에 있고, 값은 git 에 없다.
- `sync` 는 kubectl **server-side apply** 를 쓴다. 매니페스트는 표준 입력으로만 전달된다. 일반 apply 는 `last-applied-configuration` 주석에 값을 평문으로 남기기 때문에 쓰지 않는다.
- `sync` 는 사람이 실행하는 명령이다. Secret 을 사람만 만든다는 원칙(I-21)과, Secret 을 GitOps 밖에서 다루는 부트스트랩 예외(I-18)에 해당한다.

### 3. 전달: core 가 역할별로 나눠 준다
- `enikk-core-credentials` 는 **core Pod 에만** 마운트한다. 마운트는 `optional` 이라 첫 `sync` 전에도 core 는 뜬다.
- 다른 서비스는 `POST /v1/credentials` 로 필요한 이름을 요청한다. core 는 SA 토큰으로 호출자를 확인하고, 그 호출자의 역할 바인딩에 허용된 이름만 내준다(I-28).
- 허용 목록은 core Helm values 의 `roleBindings[].credentials` 에 있다. 즉 git 에 있다.
- 처리 규칙은 다음과 같다.
  - 허용되지 않은 이름을 요청하면 403 이다.
  - 허용됐지만 아직 설정되지 않은 이름이면 404 이다. 메시지에는 이름만 담는다.
  - 응답에는 `Cache-Control: no-store` 를 붙인다.
- core 는 요청마다 마운트된 파일을 다시 읽는다. `sync` 로 값을 바꾸면 kubelet 이 파일을 갱신하므로 core 를 재시작하지 않아도 반영된다. 이미 값을 받아 간 서비스에 반영할지는 그 서비스가 다시 요청하는지에 달려 있다.
- 받은 값은 각 서비스의 메모리에만 둔다. 파일, 로그, 트레이스에 쓰지 않는다.
  - 예외는 Claude 구독 토큰이다. 런타임은 이 토큰을 Agent SDK 하위 프로세스의 환경변수로만 넘긴다(I-02).
- 계약 모델에서 비밀값은 `SecretStr` 이다. `repr` 이나 Python 덤프에서는 가려지고, JSON 으로 직렬화할 때만 평문이 된다.

### 4. 전송 보안
- 클러스터 내부 통신은 평문 HTTP 를 유지한다. 단일 노드 개인 클러스터이고, SA 토큰도 이미 같은 경로로 오가고 있기 때문이다.
- TLS 는 도입하지 않는다.

## 근거
- 원본을 클러스터 밖 PC 파일에 두면 클러스터를 초기화해도 `secret sync` 한 번으로 복구된다. 외부 서비스도 필요 없다.
- 암호화하지 않으면 키 분실로 복구가 막히는 일이 없다. 대신 PC 계정 보안과 백업 매체 보관에 기댄다.
- 비밀값을 마운트하는 곳이 core 하나뿐이고, 누가 무엇을 받는지가 한 파일(core values)에 모인다.
- 다른 서비스는 Kubernetes API 토큰이 없으므로(I-28) core 를 거치지 않고는 Secret 을 읽을 방법이 없다.
- 서비스들은 원래 core 없이는 일할 수 없으므로, core 를 통해 비밀값을 받아도 새 장애 지점이 생기지 않는다.
- GitHub 저장소 시크릿에 대한 판단은 GitHub Actions 의 동작 방식에 근거한다. 시크릿은 워크플로가 실행되는 동안에만 읽히고, REST API 는 값을 돌려주지 않는다. 이 결정을 내리면서 공식 문서를 다시 확인하지는 않았다.

## 결과
- I-02, I-07 을 수정하고 I-30 을 추가한다.
  - I-02: Claude 토큰을 전달 목적으로 core 도 갖는다.
  - I-07: 비밀값은 core 의 비밀값 API 로만 전달된다.
- 평문 원본 파일이 유출되면 모든 비밀값이 유출된다. PC 계정 보안과 백업 매체 보관이 곧 비밀값 보안이다.
- core 가 손상되면 모든 비밀값이 노출된다. core 는 비밀값을 기록하지 않고, 이름만 로그에 남긴다.
- 서비스가 시작할 때 core 가 응답하지 않으면 비밀값을 받을 수 없다. 서비스는 재시도한다.
- 새 비밀값이 필요하면 다음 세 곳을 함께 바꾼다. `CredentialName` 에 이름 추가, core values 의 허용 목록, 소유자의 `secret set`.

## 재검토 조건
- 클러스터가 여러 노드로 늘거나 외부에서 접근할 수 있게 되면, 내부 TLS 와 NetworkPolicy 를 다시 검토한다.
- 사용자가 둘 이상이 되면 원본 파일 방식을 다시 검토한다.
- 비밀값 교체가 잦아지면, 서비스가 값을 다시 받아 가는 방식을 다시 검토한다.
