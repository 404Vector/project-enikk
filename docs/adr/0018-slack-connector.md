# ADR-0018: Slack 커넥터 — 연결 규칙, 중복 처리, 진행 표시

- 상태: 승인
- 날짜: 2026-11-22
- 관련: ADR-0010, ADR-0011, ADR-0012, ADR-0013, I-01, I-11, I-15, I-22, I-27

## 배경
- Slack 에서 말을 걸면 에이전트가 답하는 첫 경로(M3)의 마지막 구성요소다. 커넥터는 Slack 과 core 사이만 잇는다(I-22).
- 워크스페이스는 소유자 개인용이며 무료 요금제다.
  - 앱은 10개까지 설치할 수 있고, 오래된 메시지 기록은 보이지 않는다.
  - `assistant_view`(AI 앱 화면)는 유료 요금제 기능이라 쓰지 않는다.
- Socket Mode 는 이벤트를 받은 뒤 3초 안에 확인 응답(ack)을 요구한다. 응답하지 않은 이벤트는 다시 보낸다.
- 한 메시지가 여러 이벤트로 온다. 채널에서 봇을 멘션하면 `app_mention` 과 `message` 이벤트가 각각 온다. 두 이벤트의 `event_id` 는 다르다.

## 검토한 대안
- **Slack Bolt**: 리스너와 ack 를 프레임워크가 처리한다. 하지만 ack 시점을 core 접수 결과에 맞춰 정해야 하고, 쓰는 기능은 이벤트 수신과 메시지·반응 API 뿐이다. → `slack-sdk` 의 Socket Mode 클라이언트와 Web API 클라이언트를 직접 쓴다.
- **봇이 참여한 스레드를 커넥터가 기억**: 재시작하면 잊는다. Slack API 로 스레드를 매번 조회하면 호출이 많다. → core 에 "이어가기 전용" 이벤트를 추가해 세션이 있는지 core 가 판단한다.
- **진행 반응을 위해 커넥터가 작업 ↔ 메시지 매핑을 보관**: 재시작하면 잊는다. → core 가 outbox 메시지에 원본 이벤트 ID 를 실어 보낸다.
- **smoke 검사가 Slack 커넥터 신원을 계속 사용**: 배포된 커넥터와 같은 outbox 를 나눠 받게 되어, 서로의 메시지를 가져간다. → smoke 전용 커넥터 종류를 만든다.

## 결정

### 1. 연결 규칙 (`config/slack.yaml`, I-15)
- 소유자 멤버 ID(`owner`)의 메시지만 처리한다. 다른 사용자, 봇(자기 자신 포함), 편집·삭제 등 `subtype` 이 있는 메시지는 무시한다(I-01). 예외로 파일을 붙인 메시지(`file_share`)는 받는다(ADR-0042).
- 처리하는 메시지와 에이전트는 다음과 같다.

| 메시지 | 처리 | 새 대화의 에이전트 |
|---|---|---|
| DM | 항상 | `routes.direct_message` |
| 채널·그룹에서 봇 멘션 (`app_mention`) | 항상 | `routes.mention` |
| 채널 스레드의 멘션 없는 답글 | 그 스레드에 대화가 있을 때만 | — |
| 그 밖의 채널 메시지 | 무시 | — |

- Slack 스레드 하나가 대화 하나다(I-11). 스레드 밖의 메시지는 그 메시지를 루트로 새 스레드를 시작하고, 답은 항상 스레드에 단다. DM 도 같다.
- 이미 대화가 있는 스레드에서는 에이전트가 바뀌지 않는다(core 가 무시한다).
- 메시지 본문에서 봇 멘션은 지운다. 멘션 말고 내용이 없으면 무시한다.
- 설정 파일은 에이전트 정의와 함께 이미지에 들어간다. 소유자 멤버 ID 는 공개 저장소에 있지만 비밀값이 아니다.

### 2. core 계약 변경
- **이벤트 ID**: `slack:<채널>:<메시지 ts>`. 같은 메시지의 `app_mention`·`message` 이벤트와 Slack 의 재전송이 core 의 기존 멱등 처리로 한 작업이 된다.
- **`InboundEvent.continue_only`**: 참이면 core 는 그 대화에 세션이 있을 때만 받고, 없으면 404 로 답한다. 커넥터는 404 를 "무시"로 처리한다.
- **`OutboundMessage.source_event_id`**: 작업을 만든 이벤트 ID. 커넥터는 여기서 원본 메시지를 찾아 반응을 바꾼다. outbox 테이블에 열을 추가한다(마이그레이션 0003, 기존 행은 작업에서 채움).
- **커넥터 종류 확인**: core 는 이벤트의 대화가 호출자의 커넥터 종류인지 확인한다. 다르면 403 이다.
- **`ConnectorKind.SMOKE`**: `enikk-ops smoke` 는 ServiceAccount `enikk-smoke`(커넥터 종류 `smoke`)로 core 를 부른다. Slack 커넥터는 이 메시지를 받지 않는다.

### 3. 수신과 확인 응답
- core 에 이벤트를 넘긴 뒤(제한 2.5초) ack 한다.
  - core 가 받았거나, 의도적으로 무시하거나, 영구 오류(예: 정의되지 않은 에이전트)면 ack 한다.
  - core 에 닿지 않거나 시간이 넘으면 ack 하지 않는다. Slack 이 다시 보낸다.
- 새로 접수된 메시지에는 ack 뒤에 👀(`eyes`) 반응을 단다. 재전송된 이벤트에는 달지 않는다.

### 4. 게시 (outbox)
- outbox 를 긴 폴링으로 받아 스레드에 게시하고, 게시한 메시지를 core 에 확인(ack)한다.
  - 본문이 12,000자 이하면 `markdown_text`(표준 마크다운)로, 넘으면 `text` 로 보낸다.
  - 실패 메시지는 경고 문구를 앞에 붙인다.
- 원본 메시지의 👀 를 지우고, 답이면 ✅(`white_check_mark`), 실패면 ❌(`x`)를 단다. 반응 실패는 기록만 하고 진행한다.
  - (2026-11-25, ADR-0042) 반응 이모지는 `config/slack.yaml` 의 `reactions` 로 워크스페이스의 커스텀 이모지를 쓸 수 있다. 설정하지 않았거나 워크스페이스에 없으면 위의 Slack 기본 이모지를 단다.
- 오류 처리:
  - 일시적 오류(429, 5xx, 네트워크)는 확인하지 않고 백오프 후 다시 시도한다.
  - 영구 오류(채널 없음 등)는 기록하고 확인한다. 같은 메시지를 계속 시도하지 않기 위해서다.
- 게시는 최소 한 번이다. 게시와 확인 사이에 커넥터가 죽으면 같은 답이 두 번 게시될 수 있다.

### 5. 배포
- `deploy/helm/connector-slack`, ServiceAccount `enikk-connector-slack`.
  - Socket Mode 연결은 하나만 두므로 복제본은 1개이고, 배포 전략은 `Recreate` 이다.
  - core 용 projected token 만 마운트한다(I-28). 루트 파일시스템은 읽기 전용이다.
- Slack 토큰(봇·앱)은 시작할 때 core 에서 받는다(ADR-0013).
- Slack 앱 설정은 `deploy/slack/app-manifest.yaml` 이다. Slack 은 매니페스트를 자동 반영하지 않으므로, 바꾸면 소유자가 앱 설정 화면에 직접 붙여 넣는다.
  - 개인 워크스페이스라 권한(scope)과 이벤트를 넓게 잡았다. 나중에 필요한 기능을 앱을 다시 설치하지 않고 쓰기 위해서다.
- `slack-sdk` 와 `aiohttp` 는 connector-slack 에서만 import 한다(import-linter).

## 근거
- 멱등 키를 메시지 위치(채널, ts)로 정하면 중복의 원인(이벤트 종류, 재전송)과 상관없이 한 번만 처리된다. core 에 이미 있는 멱등 처리를 그대로 쓴다.
- 대화 존재 여부와 반응 대상은 core 가 이미 아는 정보다. 커넥터가 상태를 갖지 않으면 재시작과 재배포가 안전하다.

## 결과
- 커넥터는 상태를 갖지 않는다. 재시작해도 놓치는 이벤트는 Slack 재전송과 core outbox 가 메운다.
- 핵심 계약(`InboundEvent`, `OutboundMessage`)이 바뀌었다. 하위 호환 기본값이 없는 `source_event_id` 는 커넥터와 smoke 만 읽는다.
- 같은 답이 드물게 두 번 게시될 수 있다.
- 채널 스레드의 멘션 없는 답글마다 core 호출이 한 번 생긴다.

## 재검토 조건
- 소유자 외 사용자를 받거나, 여러 워크스페이스를 연결할 때.
- 유료 요금제로 바꿔 AI 앱 화면(`assistant_view`)을 쓰고 싶을 때.
- 중복 게시가 실제로 문제가 될 때(게시 전에 스레드를 확인하는 방식 검토).
