# ADR-0015: 런타임 공통 작업 처리 흐름

- 상태: 승인
- 날짜: 2026-11-22
- 관련: ADR-0005, ADR-0006, ADR-0010, ADR-0012, I-13, I-16, I-22, I-24, I-25

## 배경
엔진별 런타임(Claude, Gemini)은 같은 흐름으로 작업을 처리한다. core 에서 작업을 받아 프롬프트를 준비하고, 엔진을 실행하는 동안 임대를 유지한 뒤, 결과를 보고한다.
이 흐름을 `libs/runtime` 에 한 번만 구현하고, 엔진 어댑터는 포트 구현만 제공하게 한다.

정해야 할 것은 다음 세 가지다.
- 런타임이 에이전트 정의를 어디서 얻는가.
- 실패를 어떻게 분류하는가.
- 임대를 잃으면 어떻게 하는가.

## 검토한 대안
- **런타임 이미지에도 `agents/` 를 넣기**: core 와 런타임의 버전이 어긋나면 서로 다른 정의를 쓸 수 있다. → 기각.
- **실패를 모두 재시도**: 설정 오류(모델 불일치, 정의 누락)는 재시도해도 같은 결과다. 시도 횟수만 소모하고 사용자에게 알리는 것이 늦어진다. → 기각.

## 결정

### 1. 에이전트 정의는 작업 배정에 담겨 온다
- core 는 작업을 배정할 때 `TaskAssignment.definition` 에 에이전트 정의 전체를 담는다. 정의를 읽는 곳은 core 하나뿐이다(I-24).
- 배정 시점에 그 에이전트가 정의에 없거나 엔진이 다르면, core 는 작업을 배정하지 않는다. 대신 재시도하지 않는 실패로 끝내고 사용자에게 알린다.

### 2. 작업 처리 흐름 (`TaskWorker`)
- 작업은 한 번에 하나씩 받는다(롱 폴링).
- 처리 순서는 다음과 같다.
  1. 정의의 엔진이 이 런타임의 엔진과 같은지 확인한다.
  2. `PromptStore` 에서 프롬프트를 가져온다.
  3. 프롬프트의 모델을 이 엔진이 실행할 수 있는지 확인한다(`ModelEngine.accepts_model`, I-16).
  4. 엔진을 실행한다.
- 실행 중에는 남은 임대 시간의 1/3 마다 임대를 연장한다. 연장 간격은 최소 1초다.
- 임대 연장이 거부되면(409/404) 실행 중인 엔진을 취소하고 결과를 보고하지 않는다. 이 작업은 이미 core 가 다시 배정했거나 끝낸 것이다.
- 실행 시간은 에이전트 정의의 `limits.timeout_seconds` 로 제한한다.
- core 에 연결할 수 없으면 지수 백오프(1초부터 최대 30초)로 다시 시도한다.
- 결과 보고는 몇 차례 다시 시도한다. 끝내 실패하면 임대가 만료되어 core 가 작업을 다시 배정한다.
- 종료 신호를 받으면 지금 처리 중인 작업을 끝낸 뒤 새 작업을 받지 않는다.

### 3. 실패 분류
| 상황 | 재시도 | 사용자에게 보이는 사유 |
|---|---|---|
| 프롬프트 조회 실패 | 예 | 실패 사유 (I-13, 기본 프롬프트로 대체하지 않음) |
| 엔진이 보고한 실패 (`EngineError`) | 엔진이 정함 | 엔진이 정한 사유 |
| 모델·엔진 불일치, 정의의 엔진 불일치 | 아니오 | 불일치 내용 |
| 시간 초과 | 아니오 | 제한 시간 |
| 예상하지 못한 예외 | 아니오 | 일반 문구. 세부 내용은 런타임 로그에만 남긴다 |

- 사용자에게 보이는 사유에는 비밀값이 들어가지 않게 한다. 예상하지 못한 예외의 메시지를 그대로 내보내지 않는 것도 이 때문이다.

## 근거
- 정의를 core 한 곳에서 읽으면 정의 버전이 하나로 유지된다. 런타임 이미지는 정의가 바뀌어도 다시 빌드할 필요가 없다.
- 설정 오류를 바로 실패로 끝내면 소유자가 문제를 즉시 알 수 있다.
- 임대를 잃은 런타임이 결과를 보고하지 않으므로, 한 작업의 결과는 하나뿐이다.

## 결과
- 런타임은 core 가 응답하지 않으면 작업을 받을 수 없다. 이는 기존 구조(I-22)에서도 마찬가지였다.
- 시간 초과로 취소된 엔진 실행의 정리 작업(하위 프로세스 종료 등)은 엔진 어댑터가 책임진다.
- 정의 형식이 바뀌면 core 와 런타임이 같은 계약 버전을 써야 한다.

## 재검토 조건
- 런타임 하나가 여러 작업을 동시에 처리해야 할 때.
- 엔진 실행 중간 결과(진행 상황)를 사용자에게 보여 줘야 할 때.
