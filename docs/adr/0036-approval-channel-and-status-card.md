# ADR-0036: 승인 요청은 승인 채널에, 요청 스레드에는 PR 상태 카드 하나

- 상태: 승인 (§3 의 카드 내용은 2026-11-24 개정: 링크 한 줄과 머지·반려 결과만)
- 날짜: 2026-11-23
- 관련: ADR-0018, ADR-0020, ADR-0022, ADR-0023, ADR-0025, ADR-0026, ADR-0032, I-01, I-11, I-19, I-20, I-34

## 배경
소유자는 PR 관련 Slack 알림이 지저분하다고 했다(2026-11-23, Slack 요청). 이 ADR 을 쓰기 전 코드(`main` 1617929)에서 확인한 알림 위치는 다음과 같다.

- **승인 요청**(상세, [승인하고 머지] [반려] 버튼, 민감 경로 확인 창)과 검사 실패, 승인 결과: 커넥터가 `chat.postMessage(channel=<소유자 user ID>)` 로 올린다. 그래서 봇과 소유자의 DM(`D0CKW5K4DGA`)의 **최상위 메시지**가 된다. 소유자가 DM 에서 개발을 요청했으면 요청 스레드도 같은 DM 안에 있으므로, 버튼이 붙은 승인 메시지가 요청 스레드 바로 옆(같은 대화의 최상위)에 대화와 섞여 쌓인다. 요청 스레드 *안* 에 버튼이 붙지는 않는다.
- **프롬프트 승격 요청**([승격] [거절], ADR-0032): 같은 방식으로 소유자 DM 의 최상위 메시지다.
- **요청 스레드**(ADR-0025 §2, ADR-0026 §4): core 가 outbox 로 상태가 바뀔 때마다 새 글을 올린다. 작업 결과 한 줄, "검사를 통과해 승인 요청을 보냈다"(새 커밋마다 다시), "검토 스레드(소유자 DM) 링크", 머지·반려·닫힘, 배포 성공·실패. PR 하나에 4~6개 이상이다.
- **#release**(ADR-0026 §1): 배포·빌드·롤백 결과와 [되돌리기]. 요청 스레드의 배포 한 줄과 겹친다.

소유자가 원하는 것:

- 승인이 필요한 것은 승인 전용 채널(`C0CL7HZ5UQ1`, 비공개)에서 처리한다. 요청 스레드에서 승인 버튼이 보이면 안 된다.
- 요청 스레드에는 PR 상태 메시지 하나만 두고, 상태가 바뀌면 그 메시지를 고친다. 실패일 때만 새 글로 알린다.
- 두 곳을 잇는 링크는 양방향으로 유지한다. 배포 상세는 #release 에만 둔다.

## 검토한 대안
- **승인 요청을 DM 에 두고 요청 스레드만 정리**: 버튼이 대화와 같은 DM 에 계속 섞인다. → 소유자 요구로 기각.
- **상태 카드 위치를 커넥터가 기억**: 커넥터는 상태를 갖지 않고(I-22, I-25 와 같은 취지), 재시작하면 잊는다. → 기각.
- **Slack 대화 이력에서 카드를 찾음**(`conversations.replies` + 메시지 metadata): DB 가 필요 없다. 그러나 스레드마다 이력 조회가 늘고, 채널 종류마다 history 스코프에 기대며, 찾는 규칙이 Slack 표현에 묶인다. → 기각.
- **core 가 카드 위치를 DB 에 두고, 카드 갱신을 notices 큐로 보냄**: 승인 메시지 위치(`review_messages`, ADR-0020 §4)와 같은 방식이다. 테이블 하나가 늘어난다. → 채택.
- **카드 위치를 알리는 새 API**: 커넥터가 카드를 올린 뒤 위치를 알려야 한다. 새 엔드포인트 대신 이미 있는 notices 확인(ack) 요청에 담는다. 카드는 바로 그 알림을 전달한 결과이기 때문이다.

## 결정

### 1. 승인 요청은 승인 채널로 보낸다
- PR 승인 요청, 검사 실패, 승인 결과(ADR-0020)와 프롬프트 승격 요청(ADR-0032)을 승인 채널에 올린다. 상세·diff·원래 요청 스레드 링크는 지금처럼 그 메시지의 스레드 댓글이다.
- 채널 ID 는 `config/slack.yaml` 의 `approval_channel`(기본 `C0CL7HZ5UQ1`)이고, 환경변수 `ENIKK_CONNECTOR_APPROVAL_CHANNEL` 로 덮어쓸 수 있다(P-05, `deploy_notify_channel` 과 같은 방식).
- 봇이 채널 구성원이어야 한다. 비공개 채널이므로 소유자가 `/invite @enikk` 로 초대한다. 새 Slack 스코프는 필요 없다(`chat:write`, `groups:read`, `groups:history` 는 이미 있다).
- 채널 게시가 어떤 이유로든 실패하면 로그를 남기고 소유자 DM 으로 보낸다. 맨 위에 "<채널> 에 올리지 못해 DM 으로 보냅니다" 한 줄을 붙인다. DM 마저 일시적 오류면 알림을 확인 처리하지 않아 다음 조회에서 채널부터 다시 시도한다(ADR-0026 §3 과 같은 코드).
- 날짜별 대화 요약 실패 알림(ADR-0035)은 승인이 아니므로 소유자 DM 에 둔다. 배포 알림은 #release 그대로다.

### 2. 버튼은 채널에서도 소유자만 실행한다
- 승인 채널의 [승인하고 머지] [반려] [승격] [거절] [되돌리기] 는 누구나 볼 수 있다. 커넥터는 누른 사람의 user id 가 `owner` 인지 확인하고(I-01), 아니면 core 를 호출하지 않고 메시지도 바꾸지 않으며 그 사람에게만 정해진 거절 안내(`chat.postEphemeral`)를 보낸다. ADR-0026 §2 의 [되돌리기] 와 같은 코드다.
- 프롬프트 결정은 core 도 `decided_by` 가 소유자인지 다시 확인한다(ADR-0032). PR 승인은 지금처럼 커밋 SHA 에 묶인다(I-33).
- 처리하면 승인 메시지의 버튼을 결과 문구로 바꾼다(기존). PR 이 Slack 밖에서 닫히면 core 가 그 승인 메시지 위치를 알림에 담아, 새 메시지 대신 같은 메시지를 "닫힘"으로 고친다.

### 3. 요청 스레드에는 PR 상태 카드 하나
> **개정 (2026-11-24, 소유자 결정)**: 소유자는 요청 스레드에 PR 내용이 붙으면 지저분하다고 했고, 카드의 단계 표시가 승인 채널의 버튼·상태와 따로 놀아 헷갈린다고 했다. 그래서 카드는 **한 줄**로 줄인다: 승인 채널 스레드 링크(GitHub PR 링크는 두지 않는다, 승인 메시지가 아직 없으면 승인 채널 링크)와 결과(머지됨 / 반려됨 / 닫힘)만. 위임 결과 한 줄도 GitHub 링크 없이 PR 번호만 적는다. 검사 중·검사 실패·승인 대기·머지 거부는 카드에 적지 않고, 커밋·설명·#release 링크도 없다. 머지 뒤의 빌드·배포·롤백 단계는 "머지됨"으로 둔다(결과는 #release 에 있다). **실패해도 요청 스레드에 새 글을 올리지 않는다**(아래 "실패만 새 글" 은 대체됨). core 가 보내는 카드 알림과 위치 저장(`status_cards`)은 그대로이고, 보이는 내용만 커넥터(`blocks.status_card`)가 줄인다.

- 개발 역할의 PR(`agent/<세션 ID>` 브랜치, ADR-0025)마다 요청 스레드에 **상태 카드** 하나를 둔다. 버튼은 없다. PR 링크, 단계, 커밋, 한 줄 설명, 승인 메시지 링크, 배포 단계면 #release 링크만 담는다.
- 단계: 새 커밋 검사 중 → 검사 실패 / 승인 대기 → 승인·머지됨(빌드·배포 중) / 머지 거부 / 반려 / 닫힘 → 배포됨(커밋) / 배포 실패 / 이미지 빌드 실패 → (되돌리면) 롤백됨 / 롤백 실패.
  - "빌드 중"을 따로 알리는 신호는 없다. 머지 단계가 "빌드·배포 중"을 뜻하고, 배포할 것이 없는 변경(문서 등)은 머지 단계로 끝난다.
- core 는 단계가 바뀔 때 카드 알림(`PullStatusCard`)을 notices 큐에 넣는다. outbox 의 상태 한 줄(ADR-0025 §2 표)은 더 올리지 않는다. 위임 결과 한 줄(PR 링크, ADR-0026 §4)은 그대로 둔다.
- **처음 한 번만 새 글**: 커넥터는 카드가 아직 없으면 요청 스레드에 올리고, 그 위치를 notices 확인 요청(`NoticeAck.cards`)에 담아 core 에 알린다. core 는 DB `status_cards`(저장소, PR 번호 → 채널, ts)에 둔다. 이후 카드 알림은 core 가 내줄 때 그 위치를 채우고, 커넥터는 `chat.update` 로 같은 메시지를 고친다.
- **순서**: core 는 같은 PR 의 다른 알림(승인 요청 등)이 같은 묶음에 있으면 카드를 그 다음 조회로 미룬다. 같은 PR 의 카드도 묶음마다 하나만 내준다. 그래서 카드는 승인 메시지가 생긴 뒤에 그 링크와 함께 나오고, 한 번 올린 카드의 위치를 core 가 안 뒤에 다음 갱신이 나간다.
- ~~**실패만 새 글**~~ (2026-11-24 개정으로 대체, 요청 스레드에 새 글 없음): 검사 실패, 머지 거부, 배포 실패, 이미지 빌드 실패, 롤백됨, 롤백 실패일 때는 카드를 고치고 요청 스레드에 한 줄을 더 올려 알림이 울리게 한다. 배포·빌드·롤백이면 "상세와 [되돌리기] 는 #release 에 있다"고 적는다.
- 롤백 결과는 되돌린 PR(롤백 PR 이 아니라 원래 PR)의 카드에도 반영한다.
- 카드를 올리지 못하면(영구 오류) 로그를 남기고 버린다. 다음 단계에서 다시 새로 올린다. `chat.update` 실패는 로그만 남긴다.

### 4. 양방향 링크
- 요청 스레드 → 승인 채널: 카드의 "승인 요청과 상세" 링크. 커넥터가 core 가 알려 준 승인 메시지 위치(`review_messages`)로 `chat.getPermalink` 를 불러 만든다. 별도 "검토 스레드 링크" 글은 올리지 않는다.
- 승인 채널 → 요청 스레드: 지금처럼 승인 메시지 스레드의 첫 댓글 "원래 요청 스레드: <링크>". 개발 역할의 보고 전문도 그 스레드에 둔다.
- permalink 를 얻지 못하면 링크 없이 나머지를 계속 보낸다.

### 5. 배포 상세는 #release 에만
- 앱별 결과, 실패 이유, [되돌리기] 는 #release 알림에만 있다. 요청 스레드에는 카드 단계와 한 줄 설명(실패한 앱 이름 등)만 둔다.

### 대체 범위
- **ADR-0020** §2-3·§4 에서 승인 요청·검사 실패·승인 결과를 *소유자 DM* 으로 보낸다고 한 부분을 대체한다(→ 승인 채널, 실패하면 DM). 승인 흐름, 커밋 SHA 고정, 머지 방식은 그대로다.
- **ADR-0023** §5 의 "승인 요청 DM 에 되돌리기 임을 표시"는 승인 채널 메시지에 표시하는 것으로 읽는다.
- **ADR-0025** §2 의 표(상태마다 요청 스레드에 새 글)를 대체한다(→ 상태 카드 하나, 실패만 새 글).
- **ADR-0026** §1 의 "승인 요청, 검사 실패, 승인 결과는 계속 소유자 DM 으로 간다"와 §4(PR #43 흐름)의 요청 스레드 알림 목록·"PR 검토 스레드(소유자 DM)"·검토 스레드 링크 글을 대체한다. 배포 알림 위치(§1), [되돌리기] 소유자 확인(§2), 채널 실패 시 DM(§3)은 그대로다.
- **ADR-0032** §2 의 "승격 요청 DM"을 승인 채널 게시로 대체한다. 승격 절차와 core 의 소유자 확인은 그대로다.
- 모두 부분 대체이므로 상태는 `승인` 으로 두고, 해당 위치에 이 ADR 로 대체됐다는 표시를 단다.

## 근거
- 버튼을 누른 사람의 확인은 Socket Mode 로 받은 상호작용의 `user.id` 로 한다. 채널과 DM 에서 같은 코드가 확인하므로 승인 채널로 옮겨도 권한은 약해지지 않는다(ADR-0026 근거와 같다). 이 PR 에서 소유자 확인 코드는 바꾸지 않았다.
- 비공개 채널에 `chat.postMessage`·`chat.update`·`chat.getPermalink` 를 쓰려면 봇이 구성원이어야 한다고 알고 있다. 이 ADR 을 쓰면서 Slack 문서를 다시 열어 보지는 않았다. 반영 뒤 실제 호출로 확인한다(실패하면 §1 의 DM 폴백과 로그로 드러난다).
- 카드 위치를 승인 메시지 위치(`review_messages`)와 같은 방식으로 core 에 두면 커넥터는 상태 없이 남는다.

## 결과
- DB 테이블 `status_cards` 를 추가한다(마이그레이션 0012). 추가만 하므로 이전 코드는 그대로 동작한다(I-34). 이미지를 되돌려도 테이블은 남고 쓰이지 않을 뿐이다.
- notices 에 새 종류(`pull-status`)가 생긴다. core 가 커넥터보다 먼저 바뀌는 잠깐 동안 이전 커넥터는 이 알림을 읽지 못해 알림 조회가 실패한다(커넥터가 재시작될 수 있다). 알림은 확인되지 않은 채 남아 있다가 새 커넥터가 전달한다.
- 승인 채널의 다른 구성원도 PR 제목, 요약, 바뀐 파일, diff 를 본다. 저장소가 공개이므로 새로 드러나는 정보는 없다고 본다. 버튼은 소유자만 실행된다.
- 이 변경 전에 열린 PR 은 카드가 없으므로 다음 단계에서 카드가 새로 생긴다. 이전 방식의 상태 글은 남는다.

## 재검토 조건
- 승인 채널에 여러 사람이 들어와 버튼 노출이 문제가 될 때.
- 한 스레드에서 여러 PR 을 동시에 진행하게 될 때(ADR-0025 재검토와 함께) → 카드가 PR 마다 하나씩 생기므로 동작은 하지만 보기 방식을 다시 본다.
