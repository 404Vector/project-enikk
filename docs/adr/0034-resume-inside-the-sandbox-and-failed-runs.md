# ADR-0034: 세션 이어받기를 샌드박스 안에서 하고, 실패한 실행을 자세히 남긴다

- 상태: 승인 (샌드박스 쓰기 경로는 ADR-0037 3b 로 부분 대체)
- 날짜: 2026-11-23
- 관련: ADR-0014, ADR-0017, ADR-0027, ADR-0029, ADR-0033, I-07, I-25, I-37, ADR-0037

> ADR-0037 3b 가 부분 대체한다. 재개할 세션을 SDK 가 `scratch_dir` 아래에 풀어 놓으므로 전에는 `scratch_dir` 전체를 쓰기로 열었다. 이제 엔진은 그 실행의 홈만 열고, 실행기(`enikk-claude-launch`)가 받은 `CLAUDE_CONFIG_DIR`(재개 디렉터리)를 쓰기 경로에 더한다. 같은 Pod 에서 동시에 도는 다른 작업의 홈은 쓸 수 없다.

## 배경
PR #64(ADR-0033)가 2026-11-23 05:36 UTC 에 배포된 뒤, assistant 작업이 `Claude Code process failed (ResultError)` 로 실패했다. 한 번 실패한 Slack 스레드는 이후 메시지도 모두 실패했다. 처음에는 웹 검색(WebSearch)이 원인으로 보였다. 로그에는 예외 이름만 남아 원인을 알 수 없었다.

**작업 기록으로 확인한 것 (진단 도구, ADR-0029)**
- 실패한 작업 4건(c3b116b8, d4b4923f, db634756, bbb9badb)은 모두 앞 작업의 세션을 이어받는(resume) 작업이었다. 각 스레드의 **첫 메시지**(587642eb, b15fa239)는 배포 뒤에도 성공했다.
- 실패한 입력 중 "이제 뭐 남았어?", "??", "아니야 그런거 안쓸거야…" 는 웹 검색과 관계가 없다. "웹검색 도구 사용 가능한 상태인거야?" 도 그 스레드의 두 번째 메시지였을 뿐이다.

**원인 (개발 Pod 에서 실제 CLI 와 가짜 API 로 재현)**
- 세션 기록은 core 에 있다(ADR-0014). SDK 는 이어받기 전에 그 기록을 `tempfile.mkdtemp()` 로 만든 임시 폴더(기본은 `/tmp/claude-resume-*`)에 풀어 놓고, CLI 의 `CLAUDE_CONFIG_DIR` 를 그 폴더로 바꾼다.
- ADR-0033 의 Landlock 샌드박스에서 `/tmp` 는 읽을 수도 쓸 수도 없다. 그래서 CLI 는 기록을 찾지 못하고 `No conversation found with session ID: …` 오류 결과를 낸 뒤 끝났다. SDK 는 이것을 `ResultError` 로 던진다.
- 같은 테스트를 Landlock 없이 돌리면 이어받기가 성공한다. 그래서 원인은 샌드박스의 경로 제한과 SDK 의 임시 폴더 위치가 어긋난 것이다.
- 매번 같은 세션 ID 로 이어받으므로 재시도 3번이 모두 5초 안에 같은 이유로 실패했다. c3b116b8 의 첫 시도가 2분 걸린 것은 배포로 Pod 가 바뀌는 중이었기 때문이다.

**WebSearch 에 대해 확인한 것**
- 실제 CLI 에서 WebSearch 의 검색 요청을 가짜 API 가 400 으로 거부하게 하면, CLI 는 그 오류(`API Error: 400 …`)를 도구 결과로 모델에 돌려주고 대화를 이어 간다. 작업은 실패하지 않는다.
- 운영 환경에서 WebSearch 가 실제로 동작하는지는 소유자의 지시에 따라 시험하지 않았다(ADR-0033 남는 위험 9 그대로).

## 검토한 대안
- **샌드박스에 `/tmp` 를 연다**: 가장 간단하다. 그러나 `/tmp` 에는 다른 작업의 풀어 놓은 기록과 임시 파일이 있을 수 있고, ADR-0033 의 경로 제한을 약하게 한다. → 기각.
- **런타임 Pod 의 `TMPDIR` 를 scratch 폴더로 바꾼다(배포 설정)**: 코드는 그대로지만, 엔진의 정확성이 배포 설정에 달린다. 개발 Pod·테스트에도 같은 설정이 필요하다. → 기각.
- **SDK 가 이어받기 기록을 풀어 놓는 동안만 Python 의 임시 폴더를 그 작업의 홈(scratch 아래, 샌드박스 쓰기 허용)으로 바꾼다**: 엔진 안에서 끝나고, 기록은 작업 홈과 함께 지워진다. 프로세스 전역 값을 잠시 바꾸지만, 런타임과 개발 Pod 는 작업을 한 번에 하나만 실행한다. → 채택.
- **WebSearch 를 끄고 Brave 검색을 붙인다**: 원인이 WebSearch 가 아니었고, 소유자는 Claude 자체 검색 도구를 쓰기를 원한다(2026-11-23). → 하지 않는다. ADR-0033 의 "웹 검색 대안"은 그대로 둔다.

## 결정
1. **이어받기 기록은 샌드박스 안에**: 엔진은 SDK 를 실행하는 동안 Python 의 임시 폴더(`tempfile.tempdir`)를 그 작업의 홈으로 둔다. SDK 가 푼 기록과 설정은 샌드박스가 허용한 경로 안에 있고, 작업이 끝나면 홈과 함께 지워진다. 샌드박스의 허용 경로는 바꾸지 않는다.
2. **실패를 자세히 남긴다**: 실행이 실패하면 런타임 로그에 결과 subtype, `is_error`, API 상태, `terminal_reason`, 오류 메시지, 결과 글, 마지막으로 부른 도구, CLI stderr 의 마지막 20줄을 남긴다. 작업의 실패 사유(Slack 스레드에 그대로 보인다)에는 한 줄 요약을 적는다. 예: `Claude stopped: error_during_execution: No conversation found … (last tool WebSearch)`.
   - 모든 글은 커널의 비밀값 패턴으로 가리고 자른다(I-07).
   - CLI 프로세스가 결과 없이 깨진 경우의 예외 메시지는 로그에만 남기고, 실패 사유에는 예외 이름만 적는다(이전과 같다).
3. **재시도는 API 오류에만**: 같은 입력으로 다시 돌려 달라질 수 있는 것은 API 오류뿐이다. 실패 결과는 다음일 때만 재시도할 수 있다고 core 에 알린다.
   - API 상태가 있고 400, 401, 403, 404, 413 이 아니다(예: 429, 5xx, 529).
   - API 상태 없이 `terminal_reason` 이 `api_error` 다(연결 끊김 등).
   - 그 밖의 오류 결과(이어받기 거부, `error_during_execution`, 턴·예산 한도)는 재시도하지 않는다.
   - 결과 없이 CLI 프로세스가 깨진 경우는 이전처럼 재시도한다.
4. **이어받기에 실패하면 같은 작업 안에서 새 세션으로**: 이어받은 실행이 모델의 답(API 오류가 아닌 턴)이 나오기 전에, 재시도로 풀리지 않는 이유로 실패하면 엔진은 이어받기 없이 한 번 더 실행한다.
   - 새 세션의 입력 앞에는 core 에 저장된 이전 대화의 마지막 부분을 글로 붙인다. 사용자·답의 글만 넣고 도구 호출과 결과는 뺀다. 한 메시지 2,000자, 합쳐 12,000자까지, 최근 것부터 넣는다.
   - 스레드에 그 사이 올라온 글(ADR-0027)과 기억(ADR-0028)은 원래 입력에 들어 있으므로 그대로 이어진다.
   - 새 세션이 성공하면 core 가 그 세션 ID 를 스레드에 묶는다. 실패한 실행의 세션 ID 는 원래 저장되지 않는다(성공한 결과만 묶는다).
   - 이미 답을 내기 시작한 실행은 다시 시작하지 않는다. 도구가 한 일을 되풀이할 수 있기 때문이다.
   - API 오류처럼 재시도로 풀릴 수 있는 실패는 새 세션으로 바꾸지 않고, 같은 세션으로 core 의 재시도를 받는다.

## 근거
- 실패가 이어받기에서만 났고, 실제 CLI 로 같은 실패(`No conversation found`)를 재현했으며, 임시 폴더를 바꾸자 같은 테스트가 통과했다(`test_sandbox.py` 의 `test_a_later_task_resumes_the_session_inside_the_sandbox`).
- 원인이 로그에 없어 처음에 엉뚱한 곳(WebSearch)을 의심했다. 결과의 내용과 stderr 가 있었다면 바로 알 수 있었다.
- 같은 세션을 같은 방식으로 세 번 이어받는 재시도는 같은 이유로 실패할 뿐이다.

## 결과
- 배포 전에 망가진 두 스레드(1795366132.766359, 1795419285.708829)와 bbb9badb 의 스레드는 이 변경이 배포되면 다음 메시지부터 원래 세션을 이어받는다. 기록은 core 에 그대로 있다. 이어받기가 다른 이유로 거부돼도 새 세션으로 답한다.
- 새 세션으로 바뀌면 도구 사용 내역 같은 엔진 내부 맥락은 사라진다(ADR-0014 가 기각한 "매번 새 세션"을 실패할 때만 감수한다).
- 결정적인 실패는 core 가 재시도하지 않으므로 한 번에 실패 사유가 Slack 에 보인다.
- SDK 가 이어받기 기록을 푸는 위치(`tempfile.mkdtemp()`)에 기대고 있다.

## 재검토 조건
- SDK 가 이어받기 기록의 위치를 옵션으로 받게 되면 → 전역 임시 폴더를 바꾸는 대신 그 옵션을 쓴다.
- 런타임이 작업을 동시에 여러 개 실행하게 되면 → 작업마다 임시 폴더를 바꾸는 방식을 다시 본다(ADR-0033 재검토 조건과 같다).
- 새 세션으로 바뀌는 일이 자주 생기면 → 이어받기 실패의 다른 원인을 찾는다.
