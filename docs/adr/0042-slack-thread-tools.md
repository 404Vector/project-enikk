# ADR-0042: 세션이 자기 스레드에 파일과 반응을 보낸다

- 상태: 승인 (1단계: 파일 보내기·반응·첨부 메시지 받기. 2단계는 아래 "이행 순서")
- 날짜: 2026-11-25
- 관련: ADR-0002, ADR-0018, ADR-0022, ADR-0028, ADR-0033, ADR-0037, I-01, I-05, I-22, I-25, I-27, I-34, I-37

> 결정은 2026-11-25 소유자가 Slack 스레드에서 확정했다(묶음 A·B 채택, PR 세 개로 나눔).

## 배경

- 에닉은 스레드에 글만 올릴 수 있었다. 만든 파일(이미지, 문서)을 소유자에게 건넬 길이 없어, 저장소에 넣어 PR 로 보내는 것 말고는 방법이 없었다.
- 커넥터는 subtype 이 있는 메시지를 모두 버렸다. 파일을 붙인 메시지는 subtype `file_share` 로 오므로, 소유자가 파일과 함께 보낸 글은 에닉에게 닿지 않았다.
- 소유자는 Slack 이 지원하는 기능을 에닉이 쓰기를 원했다. 다만 Slack 의 기능 대부분은 다른 사람의 메시지를 읽거나, 다른 사람에게 보내거나, 되돌리기 어렵다.

## 검토한 대안

- **Slack 공식 MCP 서버**: 기능이 많다. 그러나 사용자 토큰(소유자 계정)으로 동작해, 소유자가 볼 수 있는 모든 채널을 읽고 소유자 이름으로 보낼 수 있게 된다. 다른 사람의 글이 신뢰하지 않는 입력으로 대량으로 들어온다(I-01). → 기각.
- **Slack 의 기능 전부를 봇 토큰으로**: 다른 사람에게 보내기, 채널 만들기·초대, 삭제, 사용자 관리마다 승인 절차가 필요해진다. → 기각(묶음 C).
- **요청이 온 스레드와 소유자에게만 닿는 기능을 core·outbox 경로로**: 지금 답이 가는 길(세션 → core → outbox → 커넥터)을 그대로 쓴다. 커넥터는 여전히 core 하고만 통신한다(I-22). → 채택.

## 결정

### 범위
- **묶음 A**(이 ADR 1단계와 2단계): 파일 보내기, 소유자 메시지에 반응, 메시지 링크, 커스텀 이모지 목록.
- **묶음 B**(2단계): 소유자가 붙인 첨부 파일 읽기, 캔버스, 리스트(유료 플랜일 때만), 예약 메시지.
- **하지 않음(묶음 C)**: 다른 사람의 메시지 읽기·검색, 다른 사람에게 보내기, 채널 만들기·초대, 메시지 삭제, 사용자 관리, 소유자의 사용자 토큰.
- 모든 동작의 대상은 **요청이 온 스레드, 그 스레드에 있는 소유자의 메시지, 에닉이 만든 것**으로 묶는다. 소유자에게만 닿으므로 승인 없이 한다.

### 1단계 (이 PR)
- **플랫폼 도구** `send_file(path, title)`, `react(name)`: 런타임이 제공하고 core 만 부른다(ADR-0022 의 플랫폼 도구, I-05). 기억·진단과 같이 `platform_defaults` 를 받은 정의에 준다.
- **`send_file`**
  - 런타임이 파일을 읽는다. 경로는 링크를 푼 뒤 그 세션의 worktree 나 tmp 안에 있어야 한다(ADR-0037 §7). 다른 스레드의 자료와 서비스의 파일은 보낼 수 없다.
  - 한 파일 10MiB, 한 작업 10개까지.
  - core 는 UTF-8 로 읽히는 파일에 비밀값 모양이 있으면 거부한다(기억 쓰기와 같은 검사, ADR-0028 §4). 바이너리는 검사하지 못한다. 비밀값이 있는 곳은 샌드박스가 처음부터 읽지 못하게 한다(I-37).
  - core 는 outbox 에 `file` 메시지(글은 제목)를 넣고, 바이트는 새 테이블 `outbox_files` 에 둔다. 커넥터는 메시지를 받으면 `/v1/outbox/{message_id}/file` 로 바이트를 가져와 그 스레드에 올린다(`files.uploadV2`). 전달을 확인(ack)하면 core 가 바이트를 지운다. 폴링 응답에 큰 파일을 싣지 않기 위해서다.
  - Slack 이 거부하면 스레드에 "파일을 올리지 못했다" 한 줄을 올린다.
- **`react`**: outbox 에 `reaction` 메시지(글은 이모지 이름)를 넣는다. 커넥터는 그 작업이 답하는 소유자의 메시지에만 붙인다. 다른 메시지에는 붙일 수 없다. 작업 상태 표시(접수·완료)는 건드리지 않는다.
- **첨부 메시지 받기**: 커넥터는 subtype `file_share` 메시지를 보통 메시지처럼 받고, 글 뒤에 첨부 파일 이름과 "아직 읽을 수 없다"는 표시를 붙인다. 글 없이 파일만 보내도 전달된다. 다른 subtype 은 그대로 버린다.

### 이행 순서
1. 1단계(위). 바뀌는 Slack 권한 없음(`files:write`, `reactions:write` 는 이미 있다).
2. 2단계: 메시지 링크, 커스텀 이모지 목록(`emoji:read`), 첨부 읽기(커넥터가 내려받아 그 스레드의 tmp 에 둔다, 신뢰하지 않는 자료), 캔버스(`canvases:write`), 리스트(유료 플랜일 때), 예약 메시지(그 스레드와 소유자 DM 에만). 동기 조회가 필요한 것(링크, 이모지 목록)은 core 가 커넥터에 묻는 길을 2단계에서 정한다. Slack 권한을 더하면 소유자가 앱을 다시 설치한다.
3. 반응 이모지 교체와 기억 변경 알림을 반응으로 바꾸는 일은 별도 PR 로 한다(ADR-0028 수정).

## 근거

- 파일과 반응은 소유자에게만 닿는다. 되돌릴 수 없는 일이나 다른 사람에게 닿는 일이 없으므로 승인이 필요 없다.
- 기존 경로를 쓰면 커넥터의 책임(Slack 호출)과 core 의 책임(검증, 기록)이 그대로다. 모든 동작이 outbox 에 남는다.
- Slack 공식 MCP 서버의 동작 방식(사용자 토큰, OAuth)은 2026-11-25 <https://docs.slack.dev/ai/slack-mcp-server/> 에서 확인했다.

## 결과

- 새 테이블 `outbox_files`(마이그레이션 0014, 확장만, I-34). 바이트는 전달될 때까지만 DB 에 있다.
- 새 outbox 종류 `file`, `reaction`. 이전 커넥터는 이 종류를 모르므로, core 가 먼저 배포되고 커넥터가 늦으면 이 메시지가 있는 동안 커넥터의 폴링이 실패할 수 있다. 커넥터가 배포되면 이어서 전달된다.
- 날짜별 대화 요약에는 파일 메시지가 제목으로 들어간다.
- 반응 이름이 워크스페이스에 없으면 Slack 이 거부하고 커넥터는 기록만 한다. 에닉은 이를 알 수 없다(2단계의 이모지 목록으로 확인한다).

## 재검토 조건

- 소유자 아닌 사람에게 닿는 Slack 기능이 필요해질 때.
- 파일 크기·개수 한도가 실제로 모자랄 때.
- outbox 에 바이트를 두는 것이 DB 크기에 부담이 될 때.
