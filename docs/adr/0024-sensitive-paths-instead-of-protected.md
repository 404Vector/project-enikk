# ADR-0024: 보호 경로를 막지 않고, 민감 경로로 표시해 강화된 승인을 받는다

- 상태: 승인 (목록의 범위는 ADR-0041 §1 로 부분 대체: 세 경계(비밀값, 머지·승격 승인, GitOps)에 해당하는 파일만. 강화된 승인 절차는 그대로)
- 날짜: 2026-11-22
- 관련: ADR-0007, ADR-0008, ADR-0019, ADR-0020, ADR-0023, I-17, I-19, I-20, I-21, I-32, I-33

## 배경
ADR-0007 은 에이전트 PR 이 보호 경로(불변식, ADR, CI 설정, 개발 에이전트 정의, 승인 절차 등)를 바꾸면 CI 에서 실패시키도록 했다(I-20). 그 결과 이 경로의 변경은 소유자가 Claude Code 로만 할 수 있다.

소유자는 이 플랫폼 자체의 개발도 Slack 만으로 하기를 원한다.

보호 경로를 둔 목적은, 에이전트가 자기 권한이나 승인 절차를 소유자 모르게 바꾸지 못하게 하는 것이다. ADR-0020 이후로는 이 목적을 git 바깥의 장치가 지킨다.

- `main` 머지는 소유자가 Slack 에서 승인한 커밋에만 일어난다. GitHub ruleset 이 강제하며(I-33), 에이전트 토큰에는 저장소 관리 권한이 없다(I-32).
- ruleset 은 git 이 아니라 GitHub 설정에 있다. `deploy/github/` 의 파일을 바꾸는 PR 이 머지되어도, 소유자가 적용하기 전에는 아무것도 바뀌지 않는다.
- 비밀값은 사람만 등록하고(I-21), App 키는 core 밖으로 나가지 않는다(I-32).

## 검토한 대안
- **현행 유지(CI 차단)**: 가장 안전하다. 그러나 플랫폼 자체의 변경을 Slack 으로 할 수 없다. → 소유자 요구로 기각.
- **보호 경로를 모두 해제**: 단순하다. 그러나 승인 로직이나 권한을 바꾸는 PR 이 일반 PR 과 똑같이 보여, 소유자가 무심코 승인할 수 있다. → 기각.
- **민감 경로로 표시하고 강화된 승인을 받음**: 에이전트도 바꿀 수 있지만, 승인 DM 에서 눈에 띄게 하고 한 번 더 확인받는다. → 채택.

## 결정

### 1. 민감 경로
- 에이전트가 만든 변경도 민감 경로를 바꿀 수 있다. CI 로 막지 않는다.
- 목록은 `config/sensitive-paths.yaml` 에 둔다. 처음 목록은 지금의 보호 경로와 같고, 이 목록 파일 자신을 포함한다.
- 판정은 **지금 실행 중인 core 가 가진 목록**으로 한다. 목록에서 항목을 빼는 PR 은 목록 파일을 바꾸므로 그 자체가 민감 경로 변경으로 표시된다. 바뀐 목록은 머지되고 배포된 뒤의 PR 부터 적용된다.
- 판정은 PR 을 누가 만들었는지와 관계없이 모든 PR 에 적용한다.

### 2. 강화된 승인
민감 경로를 바꾼 PR 의 승인 요청 DM 은 다음이 다르다.
- 맨 위에 "⚠️ 민감 경로 변경" 과 해당 파일 목록을 표시한다.
- 민감 경로 파일의 diff 는 첨부 파일이 아니라 본문에 바로 보인다. 길면 앞부분을 보이고, 전체는 첨부 파일로 둔다.
- [승인하고 머지] 버튼에 Slack 확인 창(confirm)을 붙인다. 소유자가 확인 창에서 한 번 더 눌러야 승인된다.
- 반려는 일반 PR 과 같다.

### 3. CI 와 저장소 설정
- `protected-paths` 워크플로를 없애고, `main` ruleset 의 필수 검사에서 뺀다. ruleset 변경은 소유자 확인 뒤에 적용한다(ADR-0020).
- 이 플랫폼 저장소의 개발 토큰에 `workflows` 권한을 준다(`config/github.yaml` 의 `workflows: true`). 워크플로 파일도 Slack 으로 고칠 수 있다. `.github/` 는 민감 경로이므로 강화된 승인을 거친다.
- ADR-0023 §5 의 "정확한 revert 는 보호 경로 검사를 통과한다" 는 필요 없어져 뺀다.

### 4. 바뀌지 않는 것
- 모든 머지는 소유자의 Slack 승인 뒤에만 일어난다(I-19, I-33). 예외를 두지 않는다.
- ruleset 은 소유자만 적용하고 끈다. 에이전트 토큰에는 저장소 관리 권한이 없다.
- 비밀값 등록은 사람만 한다(I-21). App 키는 core 밖으로 나가지 않는다(I-32).
- Slack 에 응답하는 실행용 에이전트는 git·클러스터 쓰기 권한이 없다(I-17). 변경은 격리된 개발 에이전트만 만든다.
- 운영 배포는 GitOps 컨트롤러만 한다(I-18).

### 5. 전환 순서
- ADR-0023 의 배포 결과 알림과 되돌리기를 먼저 구현한다. 민감 경로 변경이 배포를 깨뜨려도 Slack 에서 되돌릴 수 있게 하기 위해서다.
- 그다음 core 의 판정과 강화된 승인을 배포하고, 동작을 확인한 뒤 워크플로와 필수 검사를 없앤다. 그 전까지는 기존 보호 경로 검사가 유지된다.

### 6. 구현 세부 (2026-11-22)
- 목록의 항목은 `/` 로 끝나면 그 디렉터리 아래 전체, 아니면 파일 하나다. 와일드카드는 쓰지 않는다(목록이 뜻하는 바를 분명히 하려고).
- core 의 승인 모듈이 PR 의 바뀐 파일(이름이 바뀐 파일은 이전 경로 포함)을 목록과 대조해, 승인 요청에 민감 경로 목록과 그 파일들만의 diff 를 담는다.
- Slack 승인 메시지: 본문에 경고와 파일 목록, [승인하고 머지] 에 확인 창. 스레드의 첫 댓글이 민감 경로 diff 이고, 그 뒤에 일반 상세와 전체 diff 파일이 온다.
- `protected-paths` 필수 검사를 ruleset 에서 먼저 빼고, 그 다음 PR 에서 워크플로 파일을 지운다(필수 검사가 남은 채 워크플로가 사라지면 모든 PR 이 막히기 때문이다).

## 근거
- 머지 권한은 git 바깥(GitHub ruleset)에서 소유자 승인에 묶여 있으므로, 경로를 막지 않아도 에이전트가 소유자 모르게 무엇을 바꿀 수는 없다. 남는 위험은 소유자가 내용을 보지 않고 승인하는 것이며, 강화된 승인은 이 위험을 줄이는 장치다.
- 판정을 실행 중인 core 의 목록으로 하면, 판정 기준을 바꾸는 변경도 이전 기준으로 판정된다.

## 결과
- I-20 을 고친다(차단 → 강화된 승인). I-32 의 "워크플로 수정 권한 없음" 을 고친다.
- ADR-0007 안전장치 3, ADR-0008 의 워크플로 변경 주체, ADR-0019 의 `self` 저장소 설명, ADR-0020 §1 의 보호 경로 검사는 이 ADR 로 대체된다.
- **감수하는 위험**: 소유자가 diff 를 제대로 보지 않고 승인하면, 에이전트가 승인 로직이나 권한 설정을 바꿀 수 있다. 승인 로직을 잘못 바꾼 배포로 승인 경로가 깨지면 ADR-0020 의 비상 절차(소유자가 ruleset 을 직접 끔)로 복구한다.

## 재검토 조건
- 민감 경로 변경이 잦아 확인 창이 형식적인 절차가 될 때.
- 소유자 외의 사람이 이 저장소의 변경을 요청하게 될 때.
