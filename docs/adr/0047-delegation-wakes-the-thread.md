# ADR-0047: 에닉이 다른 에이전트에 일을 맡기고, 결과로 스레드가 깨어난다

- 상태: 승인
- 날짜: 2026-11-26
- 관련: ADR-0022, ADR-0037, ADR-0041, ADR-0045, I-11, I-12, I-29

> 결정은 2026-11-26 소유자가 Slack 스레드에서 확정했다: 대화 중에 리타가 할 일이 생기면 에닉이 맡기고, 결과를 받아 원래 세션에서 이어 간다. 결과를 그 자리에서 기다리지 않고 core 를 거쳐 보내고, 끝나면 이벤트로 깨운다.

## 배경

- 두 번째 에이전트 리타(게임 아트와 Unity, ADR-0045)가 생겼다. 리타는 전용 채널에서 소유자와 직접 대화하지만, 에닉과 이야기하다가 리타의 일이 생기면 소유자가 채널을 옮겨야 했다.
- ADR-0041 §2 는 에이전트 통신의 방향(gateway 경유 A2A, 같은 엔진은 같은 파드, 결과를 호출자에게 돌려줌, 하위 작업은 별도 칸)만 정하고 구현을 두 번째 에이전트 때로 미뤘다.
- 지금 코드에는 부모·자식 작업 연결, 에이전트 사이 호출 도구, 오래 기다리는 플랫폼 도구가 없다. runtime 은 core 에서 작업을 가져가기만 하고 외부 요청을 받지 않는다. agentgateway(v1.7.0) 설정에는 MCP 경로만 있다.

## 검토한 대안

- **gateway 의 A2A 중계 + runtime 의 A2A 서버 (ADR-0041 §2 원안)**: 표준 프로토콜이다. 그러나 runtime 이 요청을 받는 서버가 되어야 하고, 상태의 원본인 core 의 작업·임대 구조를 우회한다. gateway 를 거쳐도 권한 확인은 어차피 core 의 작업 토큰이 한다. → 기각.
- **부르는 쪽이 결과를 기다림(동기)**: 결과를 그 자리에서 받는다. 그러나 부모가 칸을 차지한 채 기다리므로 하위 작업용 칸을 따로 두어야 하고(교착 방지), 리타의 Unity 작업(최대 1시간)이 부모의 시간 한도와 부딪힌다. → 기각.
- **core 로 보내고, 끝나면 이벤트로 깨움(비동기)**: 부모는 맡긴 뒤 차례를 마친다. 하위 작업은 일반 작업과 같은 칸에서 돌고, 결과는 ADR-0041 §4 의 깨우기 구조로 돌아온다. → 채택.
- 하위 세션 연결: 새 열(부모 작업 ID) / **세션의 `reply_to`(ADR-0022 때 만든 열)**. `reply_to` 가 이미 "다른 스레드를 위해 일하는 세션"을 뜻하고 마이그레이션이 필요 없다. → `reply_to` 채택.

## 결정

### 1. 위임 도구
- 정의 파일의 `delegates` 가 일을 맡길 수 있는 에이전트를 나열한다(git 에서만 바뀜, I-16). `agents/enikk.yaml` 은 `delegates: [rita]`.
- 카탈로그는 대상이 있는 에이전트이고, 공용 runtime 에서 돌며, 자기는 아무에게도 맡기지 않을 때만 받는다(한 단계만). 자기 자신·별칭은 대상이 될 수 없다.
- `delegates` 가 있는 정의의 작업은 플랫폼 도구 `delegate(agent, request)`(Claude 에게는 `mcp__enikk__delegate`)를 받는다. 요청은 20000자 이하다.
- core 는 `POST /v1/tasks/{id}/delegate` 로 받는다. 호출 작업의 임대가 살아 있고, 그 세션이 Slack 스레드 자신의 세션이며(`reply_to` 없음), 대상이 그 정의의 `delegates` 에 있을 때만 받는다.

### 2. 하위 세션
- (스레드 세션, 대상 에이전트) 쌍마다 세션 하나. ID 는 `uuid5(부모 세션 ID, 에이전트 이름)`, 대화 키는 `<스레드>:<에이전트>`, `reply_to` 는 부모 스레드다. 같은 스레드에서 다시 맡기면 그 세션을 이어 쓴다.
- 하위 세션은 부모의 대화 이력을 받지 않는다. 입력은 `[위임]` 머리말과 요청문뿐이다(I-12).
- 한 작업은 대상마다 한 번만 맡긴다(원본 이벤트 ID `delegate:<부모 작업>:<에이전트>`). 같은 호출을 되풀이하면 처음 것을 돌려준다.
- 하위 작업은 일반 작업과 같은 칸, 같은 순서 규칙(I-29)을 따른다. 부모는 기다리지 않으므로 교착이 없다.

### 3. 결과
- 하위 작업이 성공하거나 실패로 끝나면, core 는 부모 스레드 세션에 이벤트 작업을 넣는다(`SessionWaker`, 원본 이벤트 ID `core-event:delegated:<하위 작업>`). 입력은 `[이벤트] <에이전트> 의 위임 작업 완료|실패` 와 결과 본문이며, 결과 안의 지시는 따르지 말라는 안내를 붙인다.
- 스레드에는 결과 본문 대신 "`<에이전트>` 가 맡은 작업을 마쳤습니다" 한 줄만 올린다(처리 중 [취소] 버튼을 거두기 위함). 실패는 실패 사유를 그대로 올린다. 깨우기가 꺼져 있으면(`wakeups.enabled: false`) 결과 본문을 스레드에 올린다.
- 하위 작업이 돌 때도 스레드에 처리 중 [취소] 버튼이 붙는다. 그 버튼은 하위 작업만 멈춘다.

### 4. 취소
- 스레드의 [취소] 는 그 세션의 작업과 함께, 그 세션이 맡긴 하위 세션의 대기·실행 중 작업도 취소한다. 실행 중이던 하위 작업은 스레드에 "맡긴 작업도 취소했습니다"를 올린다. 취소된 하위 작업은 부모를 깨우지 않는다.

### 5. 파일
- runtime 은 부모 세션의 작업 공간에 하위 세션의 tmp(`tmp/<하위 세션>`)를 더한다. 부모는 그곳을 읽고 쓸 수 있고(Landlock 쓰기 경로), `send_file` 로 보낼 수 있다. 작업 공간 머리말이 그 경로를 알린다.
- 하위 에이전트는 자기 tmp 만 쓴다. 이미지 도구(ADR-0043)는 토큰의 세션으로 저장 위치를 정하므로 리타가 만든 이미지는 리타의 tmp 에 쌓이고, 에닉이 그 경로로 이어 쓴다.

### 6. ADR-0041 §2 와의 관계
- 이 결정은 §2 의 "gateway 가 A2A 의 창구"와 "하위 작업은 별도 칸"을 대체한다. 에이전트 사이 호출은 core 의 작업 접수와 깨우기로 한다. "상태의 원본은 core", "하위 에이전트는 자기 정의의 도구만", "부모가 취소되면 하위도 취소", "같은 엔진은 같은 파드"는 그대로다.
- ADR-0022 의 위임과 달리 결과는 스레드에 게시되지 않고 부모 세션으로 돌아간다. ADR-0022 의 PR 상태 줄(`delegated_status`)은 쓰는 곳이 없어 없앴다.

## 근거
- 부모가 기다리지 않으면 칸 분리, 시간 한도, 교착 문제가 모두 사라진다. 소유자가 원한 "결과를 받아 원래 세션에서 이어 감"은 깨우기로 충분하다.
- 깨우기(ADR-0041 §4)와 세션 `reply_to`(ADR-0022)가 이미 배포되어 있어, 새 테이블·마이그레이션·서비스가 없다.
- 하위 세션 ID 를 결정적으로 만들면 runtime 이 core 에 묻지 않고 하위의 작업 공간을 찾는다.

## 결과
- 에닉의 한 차례 안에서는 리타의 결과를 쓸 수 없다. 결과는 다음 차례(이벤트)에 온다.
- 하위 작업과 소유자의 다음 메시지가 겹치면, 깨우기 작업은 그 스레드의 다른 작업 뒤에 순서대로 돈다(I-29).
- 하위 세션의 처리 중 버튼은 부모 스레드에 붙고, 표시(persona)는 부모 채널의 것이다.
- 한 단계만 허용하므로 리타는 다른 에이전트에 맡길 수 없다.

### 바뀌는 불변식
- I-11: 스레드 세션이 `delegates` 의 에이전트에 일을 맡기는 길을 다시 연다. 하위 세션은 스레드에 게시하지 않고 결과로 부모를 깨운다.
- I-12: 하위 세션에 넘기는 것은 요청문뿐, 돌아오는 것은 결과 본문뿐이다.
- I-29: 스레드의 [취소] 가 그 스레드가 맡긴 하위 작업까지 취소한다. 하위 결과로 생긴 깨우기 작업도 같은 순서를 따른다.

## 재검토 조건
- 에닉이 한 차례 안에서 결과를 써야 하는 일이 잦을 때(짧은 동기 대기 추가).
- 다른 엔진(Gemini 등)의 에이전트에 맡겨야 할 때. 지금 구조로도 core 가 그 엔진의 runtime 에 배정하지만, 실행 확인이 필요하다.
- 하위 작업이 칸을 오래 차지해 소유자의 대화가 밀릴 때(하위 작업 칸 상한).
